**Кодовая фраза: «Продолжаем ревью ORM по списку».**

При этой фразе прочитать этот файл и `learning/session.md`. Не начинать ревью заново и не выдавать уже
выполненные boolean/Date/JSON-сценарии как новые задания. После каждого законченного пункта обновлять статус,
проверки и следующий шаг здесь по запросу пользователя о фиксации прогресса.

Пункт 5 — безопасность `RetryLayer` — закрыт в рамках явного разрешения `canRetry` на уровне вызова.
Следующий участок: **пункт 6 — таймаут и отмена запроса**. Сначала различить прерывание Effect,
возврат ошибки таймаута и фактическую остановку операции БД. Исправления пункта 6 ещё не внесены.

Нумерацию исходного списка сохранять. После пункта 5 переходим к пункту 6; порядок остальных
открытых пунктов окончательно не согласован. Не подменять весь список только ближайшей задачей.

## 1. Кодирование записи и условий — основное исправлено, остаток открыт

### Закрыто в проверенных сценариях

- `INSERT`: encode значений, пропуск null, сохранность исходного IR, CodecError с исходной причиной,
  колонкой и доменным значением; при ошибке кодека запись отсутствует.
- Boolean round-trip через собственные insert/select builders на SQLite.
- `repo.save`: boolean и JSON, включая декодирование INSERT RETURNING.
- `SELECT WHERE`: Eq/Neq/сравнения порядка, And/Or/Not, In, Between обрабатываются encodePredicate.
  Boolean findBy(true/false) и ошибка WHERE-кодека закреплены постоянными тестами.
- `JOIN ON`: кодирование подключено независимо от наличия WHERE. Постоянный тест
  `encodes JOIN ON and WHERE together` проверяет оба условия вместе; исправлена потеря подготовленного WHERE.
- `UPDATE SET`: encode через общий encodeRow; `UPDATE WHERE`: передаётся sources, выполняется encodePredicate.
- `UPDATE RETURNING`: декодирование подключено. Тест репозитория проверяет false → 0 → false,
  точное SQL-хранение и неизменность соседней строки.
- `DELETE WHERE`: boolean-условие кодируется; соседняя строка сохраняется.
- `DELETE RETURNING`: выбранные id/active возвращаются с boolean, а не SQL-числом.
- `write-builders.ts`: сбор фабрик RETURNING вынесен в общую внутреннюю функцию для INSERT/UPDATE/DELETE.
- `typed-run.ts`: выделены getCodec, encodeLiteral, prepareCodecs, encodePredicate, encodeRow.
  Выбор кодека получает dialectId; encodeRow не меняет входной объект.

### Остаток и ограничения доказательств

- **LIKE:** контракт не определён. SQL-шаблоны `%`/`_` нельзя автоматически кодировать как обычное доменное
  значение: произвольный кодек может разрушить смысл шаблона. Не добавлять тег Like в общую ветку без решения.
- **Потоковый путь** `src/query/typed-stream.ts` компилирует Select отдельно от runWithSql и не использует
  описанную подготовку/декодирование. Не объявлять кодеки всех способов исполнения закрытыми.
- При рефакторинге была реальная регрессия Not: рекурсия получала сам pred вместо pred.pred и зависала.
  Исправлено. Временный SQLite-сценарий подтвердил обычное сравнение и NOT с точными разными строками;
  **постоянного регрессионного теста NOT в этой сессии не добавлено**. 38 прежних тестов не ловили зависание.
- Основные UPDATE/DELETE/JOIN boolean-сценарии проверены на SQLite, не все варианты на PostgreSQL.
  Множественные JOIN, полный набор кодеков/предикатов, ошибки/NULL во всех write-вариантах не доказаны.
- Низкоуровневые вызовы без метаданных таблицы не получают автоматически гарантии typed builders.

Уточнение исходного ревью: IR может хранить доменные литералы — encode выполняется перед compile, когда
известен диалект. SQLite-ошибка уже оборачивалась в типизированный DbError; утверждение «не типизированная»
неточно. Общий контракт должен иметь round-trip через свой API, но отдельный тест decode/WHERE вправе
использовать сырой SQL для независимой подготовки данных.

Основные файлы: `src/query/typed-run.ts`, `src/query/write-builders.ts`,
`src/query/builder.test.ts`, `src/query/write-builder.test.ts`, `src/query/make-repository.test.ts`.

## 2. Доменные типы кодеков — исходные дефекты исправлены

- withCodec сохраняет обязательную фабрику Codec<TS, SQL>; InferValue извлекает TS, InferColumn добавляет null.
  Дополнительный фантом `_ts` не вводили: существующей фабрики достаточно для вывода типа.
- json<T>() сохраняет T. timestamp() больше не имеет стирающей аннотации ColumnDef<'text'>.
- SqlType расширен `timestamp` и `json`; соответствующие конструкторы используют эти метаданные.
- Диалекты: timestamp → TIMESTAMPTZ / TEXT; json → JSONB / TEXT (PostgreSQL / SQLite).
- SqlToTs содержит timestamp: Date и json: unknown. Последнее — безопасный запасной тип; json<T>() выводит T
  через обязательную фабрику кодека, а не превращается в unknown.
- dateCodec/jsonCodec сохранили PostgreSQL passthrough и SQLite преобразования. Тип SQL теперь соответствует им.
- `preserves Date through save and findById`: фиксированный Date, SQL-тип из описания схемы, проверены
  INSERT RETURNING и findById на SQLite и PGlite.
- `encodes JSON on save and decodes the returned row`: объект `{ language: 'ru' }` через save и findById
  на SQLite и PGlite. Сырое хранение отдельно: SQLite — JSON-строка, PGlite JSONB — объект.
- Тест сначала оставлял mapCol('text') для PostgreSQL и получил '[object Object]'. Исправлен DDL теста:
  тип берётся из `_columns.payload._type`, ожидания не подгонялись под потерю данных.

Ограничения: PostgreSQL проверен через PGlite, не отдельный сервер. Generic T — не runtime-валидация JSON.
Не объявлять проверенными все допустимые JSON-значения, invalid Date, временные зоны и точность сверх Date.

Файлы: `src/schema/columns.ts`, `src/schema/infer.ts`, `src/dialect.ts`, `src/codec.ts`,
`src/query/make-repository.test.ts`.

## 3. PGlite streaming с параметрами — открыт

`src/drivers/pglite.ts`, executeStream: DECLARE выполняется через pg.exec без params; params передаются
в FETCH. Установленный API exec не принимает массив параметров, query принимает.
`src/query/typed-stream.test.ts` не доказывает PGlite streaming с параметрами.
Это подтверждено чтением кода/API; отдельный runtime-прогон этой ошибки в текущей сессии не выполнялся.
Следующий критерий: реальный потоковый запрос PGlite с параметром, точные строки, корректное освобождение
курсора при завершении/ошибке/прерывании. Не считать простой запрос без параметров достаточной проверкой.

## 4. Слои не обрабатывают executeStream — открыт

`src/layers/retry.ts`, `metric.ts`, `tracing.ts`, `slow-query-log.ts`, `statement-timeout.ts`
напрямую передают inner.executeStream. Исправлений не было.
Нужно определить поведение каждого слоя для жизненного цикла потребления потока, а не только его создания.
Не копировать retry вслепую: повтор после выдачи части строк может дублировать результат.

## 5. RetryLayer и неидемпотентная запись — закрыт

- `DriverImpl.executeRaw` принимает необязательный третий аргумент с `canRetry`.
  Без `canRetry: true` выполняется одна попытка. Разрешение означает, что вызывающий код гарантирует
  безопасность повторного выполнения, даже если первая попытка уже применила изменение.
- `RetryLayer` дополнительно проверяет временный характер ошибки и соблюдает `maxAttempts`.
  `ConnectionFailureError`, `StatementTimeoutError` и `DatabaseBusyError` сами по себе не разрешают повтор.
- `MetricLayer`, `SlowQueryLogLayer`, `StatementTimeoutLayer` и `TracingLayer` передают опции дальше.
- Постоянный тест потери ответа моделирует списание до ошибки: без разрешения наружу возвращается
  `ConnectionFailureError`, баланс остаётся `900`, а не `800`.
- Постоянные тесты проверяют лимит разрешённых повторов и отсутствие повторов постоянной ошибки
  даже при `canRetry: true`. Сценарий `DatabaseBusyError` проходит через внешний `MetricLayer`:
  потеря опций уменьшит число попыток с трёх до одной и приведёт к падению теста.
- Проверки: `pnpm test src/layers` — 10/10; `pnpm check-types` — без ошибок.
  Временный сценарий через каждую из четырёх внешних обёрток подтвердил две попытки и успех
  после первой временной ошибки при `canRetry: true`. Для остальных трёх обёрток постоянного
  теста сочетания с `RetryLayer` нет. Общий набор тестов проекта не запускался.

## 6. Таймаут и отмена запроса — открыт

`src/layers/statement-timeout.ts` использует Effect.raceFirst только для executeRaw.
Синхронный better-sqlite3 внутри Effect.try блокирует поток: таймер не прервёт выполняемый вызов.
Асинхронные PGlite/libsql операции не имеют явного подключения отмены; прерывание Effect не доказывает
остановку самой операции БД. Существующие тесты используют искусственный Effect.sleep.
Исходное «не останавливает ни фибру, ни запрос» слишком общее: различать прерывание Effect и отмену БД.
В проекте PGlite embedded; утверждения об отдельном сервере PostgreSQL сейчас не проверялись.
Нужен контракт и реальная проверка на поддерживаемом драйвере; statement_timeout/cancellation исследовать
по возможностям конкретного драйвера, не маскировать ограничение гонкой таймеров.

Проверка 2026-09-17: временный сценарий Node/tsx с реальным `sqlite.layer({ path: ':memory:' })`
и `StatementTimeoutLayer({ timeoutMs: 1 })`. Рекурсивный SQL-запрос суммировал числа от 1 до 1000000.
Наблюдение: `Success`, сумма `500000500000`, длительность вызова 159 мс вместо ошибки таймаута.
Файлы сценария не создавались; backend-код не менялся. Это подтверждает ограничение синхронного
SQLite, но не проверяет отмену PGlite/libsql. Следующий учебный шаг — объяснить, почему таймер
не может прервать синхронный вызов; затем выбрать честный контракт таймаута по возможностям драйверов.

## 7. makePool PGlite — открыт

`src/drivers/pglite.ts`: каждый acquire вызывает PGlite.create(options).
При стандартных options это независимые in-memory экземпляры. Тест `pglite-pool.test.ts` использует size: 1.
Уточнение: size: 2 сам по себе не гарантирует получение двух ресурсов при последовательном использовании;
для доказательства нужны одновременно удерживаемые два ресурса. Наличие dataDir не доказывает безопасный
пул соединений к одной базе. Эксперимент с двумя ресурсами ещё не запускался.

## 9. Остальные пункты — раздельный статус

### 9.1. Синхронные throw — открыт вопрос контракта

`makeRepository` бросает PrimaryKeyError при отсутствии PK; `selectAll` бросает QueryInvariantError при
нарушенном состоянии. Не переведены автоматически в error channel. ReturningError при пустом INSERT RETURNING
уже передаётся через Effect.die; NotFoundError/TooManyError исполнения идут по каналу ошибок.
Сначала решить, где ошибка использования синхронного конструктора, а где ожидаемая ошибка исполнения.
Нельзя механически вызывать Effect.die вместо throw без изменения возвращаемого интерфейса.

### 9.2. Alias из первой буквы — не изменён, низкий приоритет

`src/query/make-repository.ts`: t._name[0] ?? 'r'. Пока это внутренний alias однотабличного запроса,
совпадение между разными репозиториями не является доказанным дефектом. Не создавать задачу о коллизии
разных запросов; пересмотреть правило при реальной необходимости соединять источники.

### 9.3. Undefined в критериях — открыт

findBy/findMany обходят Object.entries(criteria), отдельно учитывают null, но не undefined.
exactOptionalPropertyTypes запрещает обычный типизированный вызов с явным undefined, но runtime-гарантии нет.
Нужно выбрать и проверить контракт: пропуск либо отказ; не менять смысл фильтра молча без решения.

### 9.4. executeOne / executeOneOrThrow — открыт

Весь результат загружается до выбора первой строки/проверки количества.
LIMIT 1/2 не добавлен. При изменении учитывать существующий limit/offset и семантику TooManyError.count:
сейчас поле содержит длину полученного результата; LIMIT 2 не сохраняет точное полное количество.

### 9.5. Nullable-поля в InferInsert — открыт

`src/schema/infer.ts`: необязательными становятся PK/default, но не nullable без default.
Нужно согласовать вывод типа и реальную вставку с пропущенной nullable-колонкой, включая существующие
ограничения набора колонок multi-row INSERT. Одной правки type-level недостаточно для проверки поведения.

### 9.6. Повторный alias JOIN — открыт

innerJoin/leftJoin не запрещают повторный alias, есть только предупреждающий комментарий.
Поправка к исходной рекомендации: возвращаемый тип never сам по себе НЕ запрещает вызов;
ограничение нужно на допустимом аргументе. Runtime-защита нужна для динамических имён/нетипизированных вызовов.

### 9.7. toIR через spread — частично защищён, остаток открыт

`ExecutableQuery.toIR` исключает sources/codecFactories деструктуризацией, затем использует ...rest.
Текущая утечка этих двух полей устранена, но явного построения только IR-полей нет: будущее поле состояния
может попасть в IR. Не отмечать исходный риск полностью закрытым.
