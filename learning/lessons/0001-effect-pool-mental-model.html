Pool управляет не массивом, а временем жизни

После урока ты сможешь по коду определить, что создаёт пул, почему лишний запрос ждёт и почему size: 2 для PGlite не равен двум соединениям PostgreSQL.

1. Проблема: цена находится в открытии

acquireRelease гарантирует корректное открытие и закрытие ресурса. Если каждое действие снова открывает TLS-сессию, процесс или соединение с базой, корректность остаётся, но цена открытия повторяется.

Определение

Пул ресурсов (resource pool) заранее или по спросу держит ограниченное число готовых scoped-ресурсов и выдаёт временное право использования — lease. Когда lease заканчивается, ресурс не закрывается, а возвращается в набор доступных.

  1. AcquireОткрыть ресурс один раз; сохранить finalizer.
  2. BorrowВыдать свободный экземпляр на одну работу.
  3. ReturnЗавершить работу; снова разрешить выдачу.
  4. ReleaseОстановить пул; физически закрыть ресурс.

Если свободных элементов нет, Pool.get не создаёт бесконечно новые элементы: он ждёт доступности в пределах конфигурации. В Effect это ожидание — часть эффекта, а не ручной цикл. Точная реализация установлена в проекте как effect@4.0.0-rc.108.

2. Увидь очередь

Запусти четыре запроса с размером 2, затем с размером 1. Следи не только за завершением, но и за переходом ждёт → работает.

Наблюдение: закрытие scope выдачи возвращает Driver. Физическое закрытие ресурса наступит позже — при закрытии внешнего scope пула.

3. Два Scope, две разные обязанности

Effect кодирует lifetime (время жизни) в требовании Scope. Официальное руководство формулирует правило прямо: finalizer запускается при закрытии scope — на успехе, ошибке и interruption.источник

// Упрощённые типы для текущего задания
acquire
  : Effect<DriverImpl, DriverError, Scope>

Pool.make({ acquire, size })
  : Effect<Pool<DriverImpl, DriverError>, never, Scope>

Pool.get(pool)
  : Effect<DriverImpl, DriverError, Scope>
Scope у Pool.make
Жизнь всего пула. Его закрытие запускает finalizer каждого созданного элемента.
Scope у Pool.get
Жизнь одной выдачи. Его закрытие уменьшает счётчик использования и делает элемент доступным.
Диагностический вопрос: если сделать Pool.get только один раз при сборке Layer, когда вернётся элемент? Только при остановке Layer. Значит, приложение удерживает один DriverImpl, а остальные элементы пула не участвуют в запросах. Это пул по типу, но не по поведению.

4. Привязка к твоему pglite.ts

В текущем драйвере граница ресурса уже видна:

make(options)
  └─ acquireRelease(
       PGlite.create(options),  // физическое создание
       instance.close()         // физическое освобождение
     )
  └─ Driver.of({ executeRaw })

Поэтому фраза задания «Pool<DriverImpl> поверх make()» означает: эффект make(options) становится acquire пула. Пул владеет созданными им DriverImpl и через них — экземплярами PGlite.

5. Главный поворот: PGlite — single-WASM

Обычный PostgreSQL pool размера 4 обычно держит четыре независимых сетевых соединения к одному серверу. Но документация PGlite говорит: экземпляр имеет одно exclusive connection к базе.источник

Сопоставь это с текущим make():

  • один вызов make(options) вызывает один PGlite.create(options);
  • два элемента пула требуют два вызова make(options);
  • значит, size: 2 создаёт два экземпляра PGlite/WASM, а не два соединения внутри одного экземпляра;
  • для in-memory конфигурации это, как правило, две разные базы с разным состоянием.
Что тогда даёт пул размера 1? Единое владение ресурсом, гарантированную финализацию и admission control — управляемую очередь перед единственным экземпляром. Он не повышает SQL throughput (пропускную способность): PGlite всё равно выполняет работу через одно exclusive connection.

Проверка понимания

6. Карта решения E1.8 — без готовой реализации

Ресурс
DriverImpl, который внутри владеет одним PGlite через существующий acquireRelease.
Acquire
Существующий make(options); ошибка создания остаётся типизированной.
Pool lifetime
Scope слоя/приложения: пул существует, пока доступен драйвер.
Lease lifetime
Нужно выбрать реальную единицу работы в публичном API; иначе элемент можно случайно удерживать весь срок Layer.
Размер PGlite
Настраиваемый параметр обязан иметь честную семантику. Значение больше 1 — дополнительные PGlite, не дополнительные соединения одного PGlite.
Доказательство
Наблюдаемый тест: ограничение одновременных выдач, ожидание лишнего fiber, возврат после scope и закрытие элементов при остановке пула.
