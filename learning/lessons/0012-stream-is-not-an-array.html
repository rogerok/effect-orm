E2.7 · первая граница · 7 минут

Stream — не массив.
Но этого недостаточно.

Перед реализацией full table scan научись находить место, где миллион строк может незаметно оказаться в памяти целиком.

Карта обучения · Памятка · Контракт Driver

Наблюдаемый результат E2.7

Упражнение требует выполнить full table scan миллиона строк через типизированный query API, сложить числовое поле с помощью Stream.runFold и измерить память.

В текущем проекте нижний слой уже существует. DriverImpl.executeStream объявлен; SQLite использует ленивый stmt.iterate(), PGlite — порционный FETCH. Не переписывай эти части вслепую. Незакрытая граница — типизированный адаптер от Select<R> к Stream<R, DriverError, Driver> и проверка памяти.

Фраза «через builder API» в упражнении относится к уже имеющемуся типизированному API selectAll(table). Fluent builder появляется только в уроке 3 и в этом репозитории пока отсутствует.

Сначала прогноз

Представь неверную реализацию драйвера:

executeStream(sql, params) =
  Stream.fromIterableEffect(
    executeRaw(sql, params).pipe(
      Effect.map(result => result.rows)
    )
  )

Снаружи тип — настоящий Stream<Row, DriverError>. Что произойдёт до выдачи первой строки?

Сначала объясни прогноз вслух, затем выбери ответ.

Три границы ограниченной памяти

  1. ProducerДрайвер получает строки постепенно: iterator или cursor/FETCH, а не all().
  2. AdapterТипизированный helper компилирует Select<R> и делегирует executeStream, не вызывая executeRaw.
  3. ConsumerrunFold хранит только аккумулятор, например { count, sum }.
  4. ScopeIterator, cursor и транзакция освобождаются при успехе, ошибке и прерывании.

Память ограничена только когда все границы сохраняют постепенность. Один скрытый rows: Row[], runCollect или аккумулятор с массивом снова удержит весь результат.

Тип будущего адаптера

Не пиши тело до проверки контракта. Заполни смысл трёх параметров:

streamFromSelect(
  statement: Select<R>,
  chunkSize?: number,
): Stream.Stream<R, DriverError, Driver>
R
Одна декодированная строка результата, а не массив строк.
DriverError
Ошибка компиляции/исполнения остаётся в типизированном error channel.
Driver
Зависимость нужна во время потребления потока: тогда выбираются dialect и реализация executeStream.

По исходнику установленного Effect, Stream.unwrap превращает Effect<Stream<A, ...>, ...> в один поток. Это подходящий строительный блок, когда сначала нужно получить сервис Driver, а затем вернуть созданный им stream. Это подсказка, не готовая реализация.

Потребитель обязан забывать строки

initial state: { count: 0, sum: 0 }
next(state, row): {
  count: state.count + 1,
  sum: state.sum + row.amount
}

В установленной версии Stream.runFold проходит по текущему chunk и заменяет аккумулятор для каждого элемента. Если аккумулятор состоит из двух чисел, его размер не зависит от количества строк. Если добавить rows: [...state.rows, row], full scan снова станет материализацией результата.

Что доказывает замер памяти

Два heap snapshot нужны по условию, но их разница показывает главным образом удержанную память после прохода. Она может пропустить кратковременный пик. Node предупреждает, что создание snapshot останавливает main thread и само может удвоить heap.

Поэтому проверка состоит из двух наблюдений. Сохрани snapshots для выполнения задания, а во время scan отдельно наблюдай peak heapUsed или process RSS. Сравни потоковый fold с намеренно материализующим runCollect в отдельных процессах; иначе второй прогон наследует прогретый heap первого.

Корректность памяти не заменяет корректность данных: fold должен вернуть точные count и sum, вычисляемые заранее из способа генерации миллиона строк.

Первое пользовательское действие

Ответь агенту без кода:

Почему Stream.fromIterableEffect(executeRaw(...).map(r => r.rows))
не решает E2.7, хотя наружный тип уже Stream?

Назови отдельно:
1. что к этому моменту уже находится в памяти;
2. кто должен получать следующую порцию;
3. что имеет право удерживать runFold.

По ответу выберем следующий шаг: если граница producer ясна — ты спроектируешь сигнатуру и ленивое тело streamFromSelect; если нет — разберём один pull по временной шкале.
