Effect ORM · урок 0014 · исполнение и фиксация

Запрос выполнен. Но ещё не сохранён окончательно.

Транзакция и Unit of Work не заменяют друг друга. На одном примере разберём, кто откладывает SQL, кто исполняет его и кто фиксирует изменения.

Что ты сможешь объяснить

Почему save может вернуть созданный БД id до COMMIT, а uow.register — нет. Это поможет выбрать способ работы для собственной ORM, не меняя контракт репозитория вслепую.

1. Не два состояния, а три

Начнём с обычной транзакции. Таблица пользователей пуста. База поддерживает создание ключа при вставке. 

BEGIN
INSERT Alice RETURNING id → 42
COMMIT
Запрос подготовлен
В JavaScript есть эффект. INSERT ещё не исполнялся. Созданного БД ключа пока нет.
Запрос выполнен
Внутри транзакции появилась строка. RETURNING уже вернул 42. Можно использовать ключ в следующем запросе. Вставку ещё можно откатить.
Транзакция зафиксирована
COMMIT завершился успешно. Изменение сохранено. Последующий обычный ROLLBACK эту вставку не отменит.

Транзакция не обязана откладывать SQL. Она позволяет выполнить запросы сейчас, а решение о фиксации принять после всей операции.

Источники: PostgreSQL: Transactions и RETURNING.

2. Проследи за состояниями

Нажимай «Следующий шаг». В первом сценарии остановись после первого INSERT: одна вставка уже выполнена, но зафиксированных строк ещё ноль. Затем выбери «Очередь UoW: успех» и сравни момент открытия транзакции.

Для пошаговой модели включи JavaScript. Статические последовательности приведены ниже и в памятке.

Транзакция: подготовка эффекта → BEGIN → INSERT и результат → COMMIT.

Очередь UoW: register → register → uow.commit → BEGIN → INSERT → INSERT → COMMIT → очистка очереди.

В модели нет реальной БД. Цифры показывают этапы одного последовательного сценария, соответствующие текущему коду. Это не имитация всех гарантий PostgreSQL или всех возможностей ORM.

3. Кто за что отвечает

Транзакция БД
Даёт атомарность: изменения группы запросов фиксируются вместе или отменяются вместе.
withTransaction
Управляет транзакцией: отправляет BEGIN, исполняет переданный эффект, выбирает COMMIT либо ROLLBACK.
Unit of Work
Учитывает изменения приложения и организует их запись. В твоём упрощённом варианте — хранит очередь эффектов до commit.

Unit of Work — шаблон проектирования, а не команда SQL. Другие реализации могут отслеживать изменения объектов автоматически. Твой UoW ничего не обнаруживает сам: он сохраняет только то, что передали в register.

Определение шаблона: Martin Fowler: Unit of Work. Конкретное поведение: твой unit-of-work.ts.

4. Как читается withTransaction

Сначала разбираем вызов без внешней транзакции. В transaction.ts это ветка depth === 0.

acquire
Начать
Исполнить BEGIN. Если начало не удалось, бизнес-операция не запускается.
use
Выполнить
Исполнить переданный эффект. В нём могут быть чтения, вставки и использование полученных результатов.
release
Завершить
Получить Exit — результат завершения use. Успех → COMMIT. Неуспех → ROLLBACK.

Effect.acquireUseRelease организует эту последовательность и выполнение завершающего эффекта после успешного начала. Exit — не HTTP-статус: он описывает успех, ошибку, дефект или прерывание вычисления.

Если операция вернула пользователя, withTransaction тоже вернёт пользователя — после успешного завершения транзакции. Сам вызов withTransaction(operation) лишь создаёт эффект; BEGIN отправится при исполнении этого эффекта.

Источники: transaction.ts и JSDoc acquireUseRelease установленной версии Effect. Подробнее: разбор каждой части функции.

5. Где эти механизмы соединяются

Внутри твоего uow.commit уже есть:

yield* withTransaction(
  Effect.all(effects, { concurrency: 1, discard: true }),
);

Effect.all исполняет очередь последовательно. withTransaction управляет общей транзакцией. После успеха UoW очищает очередь. При ошибке БД откатывается, а очередь остаётся: до её очистки программа не дошла.

Два разных rollback. SQL ROLLBACK отменяет уже выполненные изменения транзакции. Твой uow.rollback отбрасывает очередь и очищает карту в памяти. Он не отменяет уже завершившийся COMMIT.

discard: true означает, что результаты отдельных операций не возвращаются вызывающему коду. Поэтому запись чтения в очередь сама по себе не даст тебе найденного пользователя.

Источник: unit-of-work.ts. Важное уточнение: одна транзакция здесь содержит несколько отдельных SQL-запросов.

6. Проверь не память терминов, а прогноз

Сначала выбери ответ, затем прочитай объяснение. Ошибка здесь помогает обнаружить, какие два момента ещё смешиваются.

А. Внутри транзакции save вернул созданный БД id. COMMIT ещё не было. Что известно точно?

Выбери утверждение.

Б. Создан UoW, зарегистрированы две вставки. Внешнего withTransaction нет, commit ещё не запускался. Каково состояние?

Выбери состояние.

В. В пустую таблицу зарегистрированы две вставки с одинаковым ключом. Вторая завершилась ошибкой. Транзакционный откат успешен, но uow.rollback отдельно не вызывали. Что осталось?

Выбери результат.

Что выбрать для своего сценария

Нужен id между запросами? Используй текущий репозиторий внутри withTransaction. Пользователь и его пост могут сохраняться одной транзакцией без очереди.

Нужно сначала накопить записи? Используй UoW. В твоём проекте builder уже можно зарегистрировать как эффект. Обычный репозиторий ещё не подключён к этой очереди.

Если withTransaction вложен в другой withTransaction, используется savepoint, а не независимая транзакция. Открой короткую последовательность в памятке: там видно, почему внутренний успех ещё не означает окончательную фиксацию.

Основной первоисточник: PostgreSQL: Transactions. Начни с примера BEGIN/COMMIT, затем прочитай абзац о savepoint.

Для повторения: завтра без подсказки объясни разницу между «запрос подготовлен», «запрос выполнен» и «транзакция зафиксирована». Затем сверься с кратким словарём.

Если шаг непонятен, спроси агента: назови сценарий и номер шага. Не нужно сначала заканчивать все вопросы. Предыдущий материал: жизненный цикл Effect.
