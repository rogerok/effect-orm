«Pool в Node» — не один механизм

Разделим event loop, libuv thread pool, Worker pool, HTTP socket pool, PostgreSQL connection pool и Effect Pool по физическому ресурсу и протоколу выдачи.

← Pool изнутри · Справочник ↗

1. Сначала убираем ложную модель

Event loop — не pool. Это цикл диспетчеризации событий и callback на основном JavaScript-потоке. Наличие асинхронного API не означает, что работа выполняется в «пуле Node».

Дальнейшая судьба операции зависит от её природы:

  • сетевой I/O обычно ожидается через неблокирующие механизмы ОС и event loop;
  • часть API, для которых нет подходящего асинхронного системного вызова, Node отправляет в libuv thread pool;
  • CPU-intensive JavaScript можно явно отправить в worker_threads;
  • HTTP Agent и database driver управляют собственными пулами sockets или clients поверх runtime.

2. Карта пулов

libuv thread pool
Ресурс: native threads. Очередь: работы fs, часть crypto, dns.lookup, zlib. Lease скрыт внутри runtime.
Worker pool
Ресурс: Worker с отдельным V8 isolate. Очередь: CPU-задачи приложения. Pool строит приложение или библиотека.
http.Agent
Ресурс: TCP/TLS sockets, сгруппированные по host/port. Очередь: HTTP requests сверх maxSockets.
pg.Pool
Ресурс: PostgreSQL clients/sessions. Очередь: connect() или query(), когда нет idle client и достигнут max.
Effect Pool<A, E>
Ресурс: любое scoped-значение A. Очередь: fibers, выполняющие Pool.get, когда разрешения заняты.
Buffer pool
Ресурс: заранее выделенный slab памяти. Малые Buffer получают slices; явного checkout/return нет. Это родственная оптимизация allocation, но другой контракт.

3. Встроенный libuv thread pool

Node документирует фиксированный libuv thread pool для API, построенных поверх синхронных системных операций: почти все async fs, некоторые crypto, dns.lookup и zlib. Текущий default — 4; размер задаётся UV_THREADPOOL_SIZE до инициализации runtime.источник

100 × fs.readFile(...)
        │
        ▼
  очередь libuv work
        │
        ├── thread 1 ── task
        ├── thread 2 ── task
        ├── thread 3 ── task
        └── thread 4 ── task

96 работ ожидают не JavaScript connection,
а свободный native worker thread.

Это task pool: вызывающий код отдаёт работу и получает Promise/callback результата. Он не получает thread в руки и не вызывает release(thread).

Долгий pbkdf2 способен задержать кажущийся несвязанным fs.readFile, потому что они делят один фиксированный pool. Это contention между типами работ, а не блокировка event loop напрямую.

4. worker_threads: pool строится поверх Worker

new Worker() создаёт отдельный JavaScript thread и V8 isolate. Node рекомендует для повторяющихся задач использовать pool, потому что стоимость создания Worker может превысить пользу.источник

submit(job)
  ├─ idle Worker? ── postMessage(job)
  ├─ workers < max? ── create Worker → postMessage(job)
  └─ иначе ── enqueue(job)

Worker сообщает result
  ├─ есть queued job? ── handoff следующей работе
  └─ иначе ── Worker становится idle

Структура совпадает с уроком 0002, но lease скрыт scheduler-ом: ресурсом владеет pool, пользователь видит только задачу.

5. http.Agent: pool sockets

Agent поддерживает persistent connections и reuse. При достижении maxSockets дополнительные requests попадают в pending queue. Сокеты разделены по origin; свободный socket другого host не обслужит запрос.источник

  • keepAlive решает, оставить ли socket после запроса.
  • maxSockets ограничивает active sockets на host.
  • maxFreeSockets ограничивает idle sockets.
  • scheduling: "lifo" | "fifo" выбирает, какой idle socket переиспользовать.
  • Закрытый сервером idle socket удаляется; следующий request создаёт новый.

Здесь pool одновременно амортизирует TCP/TLS setup и ограничивает конкуренцию к endpoint.

6. pg.Pool: классический connection pool

Установленный через @effect/sql-pg pg-pool@3.14.0 хранит три центральные коллекции:

_clients      // все созданные PostgreSQL Client
_idle         // доступные Client + idle timer
_pendingQueue // ожидающие connect/query

В опубликованном исходнике алгоритм конкретен: pending request берётся через shift() — FIFO, а idle client через pop() — LIFO. Если pool не full и idle отсутствует, создаётся новый Client.исходник

pool.connect()
  ├─ idle есть       → checkout idle Client
  ├─ total < max     → new Client().connect()
  └─ total == max    → pendingQueue.push(waiter)

client.release(error?)
  ├─ broken/expired  → client.end(); pulse queue
  ├─ waiter есть     → следующий checkout
  └─ иначе           → idle + idle timeout

pool.query() безопасно делает checkout → одну query → release. Для транзакции это неверная граница: все statements обязаны выполняться на одном Client, поэтому нужен явный pool.connect() и release после COMMIT/ROLLBACK.источник

Lease задаётся session semantics, а не удобством API. Один statement может быть lease для независимой query. Транзакция, temporary table, session SET или advisory lock требуют удерживать тот же connection дольше.

7. Effect Pool: generic resource pool для fibers

Effect не знает, является A соединением, Worker или браузером. Он добавляет к общей машине три вещи:

  1. Typed acquire: Effect<A, E, Scope> описывает создание элемента, ошибку и finalizer.
  2. Scoped lease: Pool.get(pool) требует Scope; finalizer выдачи автоматически возвращает элемент.
  3. Fiber suspension: ожидающий Pool.get приостанавливает fiber, а не блокирует event loop или OS thread.
Pool.make({ acquire, size, concurrency? })

fixed capacity = size элементов
permits = size × concurrency

Pool.get(pool)
  → взять permit
  → найти/создать PoolItem
  → refCount += 1
  → добавить finalizer в scope выдачи

scope выдачи закрыт
  → refCount -= 1
  → вернуть item или уничтожить invalidated
  → вернуть permit

Это не аналог libuv thread pool: Effect fiber — лёгкая логическая задача runtime, а элемент A выбираешь ты. В точном исходнике 4.0.0-rc.108 состояние содержит items, available, invalidated, semaphore, waiters и shutdown flag.источник

Необычный параметр concurrency

Обычный DB connection чаще выдаётся одному borrower, то есть concurrency = 1. Effect разрешает несколько одновременных lease одного item. Это полезно только если сам A поддерживает безопасное совместное использование. Параметр увеличивает permits, но не клонирует физический ресурс.

8. Теперь честно про PGlite

Официальная документация: PGlite имеет одно exclusive connection к базе.источник Текущий src/drivers/pglite.ts вызывает PGlite.create(options) внутри каждого make(options).

Pool.make({ acquire: make(options), size: 4 })
До четырёх отдельных PGlite/WASM instances. Это не четыре sessions одного PGlite. Для memory-конфигурации их database state раздельно.
Один PGlite, size: 1
Pool управляет lifecycle и exclusive lease; лишние fibers ждут. Throughput базы не растёт.
Один PGlite + только лимит операций
Если acquire/destroy и identity ресурса не нужны, semaphore описывает задачу точнее. Но E1.8 специально требует исследовать Pool.make.
Будущая транзакция
Lease должен охватывать всю транзакцию, а не отдельный executeRaw; иначе statements могут попасть на разные pool items или между ними вклинится чужая работа.

Диагностическая формула

При встрече со словом pool всегда задавай пять вопросов:

  1. Какой физический ресурс переиспользуется?
  2. Что стоит в очереди при исчерпании capacity?
  3. Где начинается и заканчивается lease?
  4. Кто выполняет health check, destroy и replacement?
  5. Что реально означает size: threads, sockets, sessions, WASM instances или permits?
Следующий шаг по E1.8 — не писать Pool.make, а сначала одним абзацем определить физический ресурс и lease boundary текущего DriverImpl. Это определит архитектуру Layer и тест.
