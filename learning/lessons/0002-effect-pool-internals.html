Pool изнутри: состояние, очередь, инварианты

Не API фреймворка, а минимальная машина, из которой получаются connection pool, worker pool и Effect Pool.

1. Что делает абстракцию пулом

Пул нужен, когда имеются одновременно три свойства:

  1. Экземпляр дорог или ограничен. Соединение требует handshake; Worker — запуск нового isolate; TCP/TLS socket — установку соединения.
  2. Экземпляр можно безопасно переиспользовать. После одной работы его можно привести в допустимое состояние для следующей.
  3. Потребителей больше, чем экземпляров. Нужна политика: кто получает ресурс сейчас, а кто ждёт.
Полная концепция: pool = resource ownership + bounded capacity + wait queue + lease protocol + health/lifetime policy. Если оставить только ограничение числа операций, получится semaphore, но не pool.

2. Данные, которые хранит минимальный pool

PoolState<R, Waiter> = {
  phase: "open" | "closing" | "closed"
  max: number
  resources: Set<R>       // всё физически созданное
  idle: Deque<R>          // можно выдать немедленно
  borrowed: Map<R, Lease> // кому выдано и ещё не возвращено
  creating: number         // зарезервированные места во время async create
  waiters: Queue<Waiter>  // запросы, которым не хватило capacity
}

creating нельзя выбросить как «деталь». Если два вызова одновременно увидят resources.size = max - 1 и оба начнут асинхронный create(), лимит будет превышен. Место резервируют до ожидания создания.

Основные инварианты

total = idle + borrowed

total + creating ≤ max

idle ∩ borrowed = ∅

успешный checkout → ровно один return или destroy

phase = closed → total = 0 и waiters = 0

Инвариант — утверждение, которое должно оставаться истинным после любого перехода: успеха, ошибки, timeout, cancellation и shutdown. Именно инварианты отличают рабочий pool от массива с методом pop().

3. Алгоритм checkout

checkout():
  if phase != open:
    fail PoolClosed

  if idle not empty:
    r = removeIdleAccordingToPolicy()
    borrowed.add(r)
    return lease(r)

  if total + creating < max:
    creating += 1               // резервируем capacity до await
    try:
      r = await create()
      resources.add(r)
      borrowed.add(r)
      return lease(r)
    finally:
      creating -= 1

  waiter = enqueueCancellableWaiter()
  return await waiter

Здесь три разных результата одного API: немедленная выдача idle-ресурса, создание нового ресурса или ожидание. Поэтому latency checkout не равна latency бизнес-операции.

4. Алгоритм return: прямой handoff

return(r, health):
  require borrowed contains r
  borrowed.remove(r)

  if phase != open or health == broken:
    resources.remove(r)
    await destroy(r)
    maybeCreateReplacementForWaiter()
    return

  if waiters not empty:
    w = waiters.dequeue()
    borrowed.add(r)
    complete(w, lease(r))       // не кладём r в idle
    return

  idle.push(r)

Когда очередь не пуста, хороший pool обычно передаёт возвращённый ресурс следующему waiter напрямую. Промежуточный переход через idle создаёт лишнее состояние и окно для несправедливого перехвата.

Мини-эксперимент: нажми «Новый checkout» три раза при max = 2, затем «Вернуть первый». Третий запрос должен получить тот же ресурс прямым handoff; idle останется равен нулю.

5. Pool ограничивает очередь, но не ускоряет ресурс

Пусть независимый ресурс обслуживает одну работу в среднем за S секунд, а размер пула равен C. Грубая верхняя граница throughput:

throughput ≈ C / S

Если приходит больше работ, чем pool способен завершать, растёт waiters. Pool не создаёт производительность из воздуха: он выбирает ограниченную конкуренцию вместо перегрузки downstream-системы.

Слишком мало
Ресурс недоиспользован, checkout latency растёт даже при свободной мощности downstream.
Слишком много
Больше памяти, sockets и server sessions; contention и context switching могут уменьшить throughput.
Неограниченная очередь
Перегрузка превращается в рост памяти и latency. Нужны timeout, cancellation или отказ на admission boundary.

Именно поэтому connection pool защищает не только приложение от дорогого connect, но и сервер от неограниченного числа sessions. Официальная документация node-postgres называет обе причины: handshake и ограничение числа клиентов PostgreSQL.источник

6. Pool, semaphore и cache — разные контракты

Semaphore
Хранит разрешения, а не ресурсы. Ограничивает число одновременных входов. Не знает create, destroy, idle lifetime и health.
Pool
Владеет конкретными экземплярами. Выдаёт identity ресурса и требует завершить lease.
Cache
Ищет значение по ключу, обычно допускает одновременное чтение и вытесняет данные ради hit rate. Checkout/return не является центральным протоколом.
Queue
Хранит работы или значения. Сама по себе не создаёт и не переиспользует ограниченный набор исполнителей.
Single PGlite показывает границу: если физический ресурс ровно один и требуется только не пускать к нему более N операций, semaphore может быть честнее pool. Pool оправдан дополнительно, когда он владеет созданием/закрытием PGlite и lease соответствует неделимой работе с его session state.

7. Ошибки, которые обязан пережить production pool

  • Create failure: освободить зарезервированный slot; не оставить waiter навечно.
  • Cancellation waiter: удалить его из очереди, иначе ресурс позже уйдёт уже отменённой работе.
  • Broken resource: destroy вместо return; при спросе создать замену.
  • Double release: обнаружить нарушение протокола. В pg-pool повторный client.release() явно бросает ошибку.исходник
  • Shutdown: перестать принимать checkout, обработать waiters, закрыть idle и определить судьбу borrowed.
  • Idle failure: ресурс может умереть, пока никому не выдан; pool должен удалить его и сообщить/заменить согласно контракту.

Проверка механизма

max = 2. C1 и C2 выданы; R3 ждёт. R1 возвращает здоровый C1. Какой переход сохраняет очередь и не создаёт лишний ресурс?

Сначала проверь значения total, idle, borrowed и waiters после перехода.

Что теперь должно быть в голове

Pool — конечный автомат (state machine) над дорогими ресурсами. Его главный результат не «быстрее», а контролируемое владение при ограниченной capacity. Быстрее становится только та часть, где ресурс действительно можно переиспользовать вместо повторного создания.

Если переход в симуляторе кажется неправильным, спроси агента про конкретное состояние и инвариант. Следующий урок разберёт, почему под словом pool в Node.js скрываются четыре разных механизма.
