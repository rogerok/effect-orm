Контракт E2.6

Три конкурентных вызова getPostsByUserId(1 | 2 | 3) должны создать три логических результата, но resolver выполняет один физический SQL с WHERE userId IN (...).

Главная новая сложность — кардинальность один-ко-многим (one-to-many). Пример курса getUserById строит индекс id → User. В E2.6 нужен индекс userId → Post[]. Замена значения в Map с одного объекта на массив меняет алгоритм раздачи ответов.

В проекте уже есть необходимые нижние части: isIn, selectAll, run и сервис Driver. Таблицы posts и DataLoader пока нет — их предстоит написать тебе.

Две роли, которые нельзя смешивать

Request
Описывает одно логическое желание: «дай все посты пользователя X». Payload хранит userId; success-тип описывает массив постов; error и services сохраняют DriverError и Driver.
RequestResolver
Получает несколько ожидающих Request.Entry, выполняет общую работу и завершает каждый entry его собственным результатом.
SQL
Возвращает плоский набор строк для всех запрошенных пользователей. SQL не знает, какой entry ждёт какой подмассив.
groupBy
Восстанавливает потерянную границу: группирует плоские строки в Map<userId, Post[]>.

Тип success одного request — не «весь результат батча», а результат одного userId. В стиле текущего проекта это естественно записать как ReadonlyArray<Post>; упражнение использует эквивалентную по форме запись Post[].

Проследи данные слева направо

  1. СобратьИз каждого entry взять entry.request.userId.
  2. ЗагрузитьОдин SELECT ... WHERE userId IN (...).
  3. СгруппироватьКаждую строку добавить в массив по её row.userId.
  4. РаздатьКаждый entry завершить массивом своей группы или [].
entries: userId 1, userId 2, userId 3
                         │
                         ▼
SQL rows: P10(userId=1), P11(userId=1), P30(userId=3)
                         │
                         ▼
index: 1 → [P10, P11]
       3 → [P30]
                         │
                         ▼
answers: request(1) → [P10, P11]
         request(2) → []
         request(3) → [P30]

Entry для userId=2 нельзя пропустить. Публичный контракт RequestResolver требует завершить все принятые entry. Если resolver успешно закончится, оставив entry незавершённым, runtime завершит его дефектом «RequestResolver did not complete request». Отсутствие постов — успешный пустой массив, не отсутствие ответа.

Алгоритм без готовой реализации

Это схема ответственности, а не вставляемый TypeScript:

resolver(entries):
  userIds = взять userId из каждого entry
  rows = выполнить один select posts where userId in userIds

  byUserId = пустой индекс
  для каждой row:
    добавить row в массив byUserId[row.userId]

  для каждого entry:
    posts = byUserId[entry.request.userId] или пустой массив
    завершить entry успешным posts

Ошибка общего SQL не превращается в []: это настоящая DriverError. Пустой массив означает только «SQL выполнился, но строк для этого пользователя нет».

Почему вызовы должны встретиться

В установленном effect@4.0.0-rc.108 RequestResolver.make откладывает запуск батча через Effect.yieldNow. Конкурентные request успевают попасть в один ожидающий batch; последовательный yield* ждёт первый ответ до создания второго request.

Effect.forEach([1, 2, 3], getPostsByUserId,
  { concurrency: "unbounded" })
// наблюдение: resolver получает [1, 2, 3]

const a = yield* getPostsByUserId(1)
const b = yield* getPostsByUserId(2)
// наблюдение: resolver получает [1], затем [2]

Изолированный запуск на текущей версии подтвердил именно эти батчи. Он также показал, что одинаковые request [1, 1, 2] доходят до resolver как [1, 1, 2]. Поэтому не опирайся на утверждение курса об автоматической дедупликации: в этой RC её нет в реализации request batching.

Проверка границы

Общий SQL успешно вернул посты только для userId 1 и 3. Что должен получить request для userId 2?

Сначала объясни причину вслух, затем выбери ответ.
Разбор для печати и чтения без JavaScript

Правильный ответ — пустой массив. [] является корректным значением отношения «у пользователя ноль постов» и сохраняет единый success-тип для всех userId.

Первое пользовательское действие

Пока не пиши resolver. Сначала опиши агенту четырьмя строками контракт будущего request:

payload  = ?
success  = ?
error    = ?
services = ?

Затем одним предложением объясни, почему success относится к одному userId, хотя SQL обслуживает весь batch. По ответу выберем следующий шаг: тип request либо механический проход entries → ids → rows → groups → completion.

Первоисточник

Начни с публичных контрактов установленной версии: Request.ts для Request<A, E, R>, TaggedClass и Entry; затем RequestResolver.ts для make и обязанности завершить каждый entry.

Урок вводит только центральную границу E2.6: один физический batch должен породить отдельный массив для каждого логического request. Задавай агенту любые вопросы по непонятным местам; backend-код и acceptance-тест остаются твоей работой.
