Разобраться в конкурентности через три независимых вопроса: какая fiber исполняется, какой Scope владеет временем жизни и кто держит ограниченный ресурс пула.

Карта обучения · Памятка выбора API · Справочник Pool

Не одна магия, а четыре механизма

Effect<A, E, R>
Описание вычисления. Пока runtime его не запустил, работа не происходит.
Fiber<A, E>
Одно живое исполнение Effect: running, suspended или завершённое с Exit.
Scope
Граница времени жизни. Хранит finalizers и запускает cleanup при закрытии.
Pool
Владелец ограниченного набора ресурсов. Pool.get выдаёт lease до закрытия checkout Scope.

Fiber отвечает «кто сейчас исполняет?»; Scope — «до какого события это обязано жить?»; Pool — «кому сейчас разрешено пользоваться дефицитным ресурсом?». Если смешать эти вопросы, fork начинает казаться случайной магией.

Как программа оживает

  1. ОписаниеКомбинаторы строят Effect. Ничего ещё не исполняется.
  2. ЗапускrunPromise создаёт root fiber и передаёт её scheduler.
  3. ИсполнениеFiber выполняет операции до результата или точки suspension.
  4. ЗавершениеПолучается Exit; children прерываются, Scope закрываются, finalizers исполняются.

Scheduler — диспетчер: он даёт fiber возможность продолжить выполнение. Fiber — не OS thread. Ты можешь иметь тысячи ожидающих fibers на одном JavaScript thread, потому что ожидающая fiber не крутит цикл и не удерживает стек вызовов как синхронная блокировка.

Зачем нужен этот sleep

Effect.sleep не «тормозит программу». Он приостанавливает текущую fiber на scheduler duration, не блокируя JavaScript thread. Остальные runnable fibers продолжают работать.

В учебных примерах sleep делает невидимое ожидание видимым. В реальном backend на том же месте обычно находится:

  • ожидание HTTP response или PostgreSQL socket;
  • ожидание очереди либо semaphore permit;
  • retry/backoff, timeout либо периодический heartbeat.

Убирать sleep из production-кода нужно, если он маскирует race condition или «даёт другой задаче время». Но для настоящей задержки, backoff и тестовой модели latency это нормальная операция. В тестах TestClock.adjust продвигает виртуальное время без реального ожидания. 

// F0 паркуется; JavaScript thread свободен
const rows = yield* databaseCall

// Нужна независимая работа — только тогда появляется новая fiber

Прокрути пять жизненных циклов

Иди кнопкой «Шаг». На каждом состоянии одновременно сверяй три колонки: Fiber tree, Scope lifetime и Pool. Автопрокрутка полезна только после ручного прохода.

Ключ к Pool-сценарию: закрытие checkout Scope возвращает Driver в пул; закрытие pool Scope физически освобождает Driver. Это два разных finalizer и два разных события.

Когда вообще дёргать fork

По умолчанию — не дёргать. Сначала выбери высокоуровневый комбинатор, который выражает требуемый результат. Ручной fork нужен, когда тебе действительно нужен Fiber-handle или особая граница времени жизни.

Обычная зависимость
yield* effect. Текущая fiber ждёт значение и продолжает с ним.
Много результатов
Effect.all(effects, { concurrency: N }). Runtime создаёт и собирает конкурентную работу.
Нужен handle
forkChild, затем Fiber.join, Fiber.await или Fiber.interrupt.
Жизнь равна Scope
forkScoped для текущего Scope; forkIn для явно выбранного Scope.
Пережить родителя
forkDetach — редкое исключение с явным shutdown-контрактом. Иначе получишь утечку или потерянную ошибку.

В установленном effect@4.0.0-rc.108 общего Effect.fork нет. Старые материалы с таким именем не копируй механически: здесь явный безопасный вариант называется forkChild.

Как управлять полученной Fiber

Fiber.joinДождаться и встроить её успех/ошибку в текущий workflow.
Fiber.awaitПолучить полный Exit как значение и самостоятельно разобрать success/failure/interruption.
Fiber.interruptПопросить остановиться и дождаться завершения interruption/finalizers.
забыть handleДопустимо лишь когда lifetime уже надёжно принадлежит parent или Scope и результат сознательно не нужен.

join не запускает Effect второй раз. Он наблюдает уже запущенную fiber. Если дочерняя fiber завершилась раньше, join сразу получает сохранённый Exit.

Модель прерывания без мистики

parent завершился / Scope закрылся / Fiber.interrupt
                    │
                    ▼
          child получает interrupt
                    │
                    ▼
       обычное продолжение прекращается
                    │
                    ▼
      finalizers освобождают ресурсы
                    │
                    ▼
          Exit содержит interruption

Interruption кооперативное: Effect runtime обрабатывает его на безопасной точке. Долгий синхронный JavaScript, блокирующий event loop, нельзя остановить посередине инструкции. Поэтому CPU-тяжёлый цикл не становится безопасно конкурентным только из-за обёртки в fiber.

Один реальный разбор проекта

Открой src/drivers/pglite-pool.test.ts и для строк с двумя Effect.scoped подпиши на бумаге:

  1. какой Scope владеет самим pool;
  2. какой Scope владеет первой выдачей Pool.get;
  3. какое событие возвращает PGlite в pool;
  4. какое событие окончательно закрывает PGlite.

Правильная проверка: второй checkout получает тот же живой экземпляр после закрытия первого checkout Scope, а физический release происходит только при закрытии внешнего pool Scope.

Первоисточники

Основной источник — JSDoc и сигнатуры установленной версии: Effect.ts, разделы sleep, scoped, forkChild, forkIn, forkScoped, forkDetach; затем Fiber.ts, Scope.ts и Pool.ts.

Этот урок — тематический мост к безопасной конкурентности ORM: fibers исполняют запросы, checkout Scope возвращает соединение, pool Scope освобождает физические ресурсы. Если любой шаг симулятора непонятен, задай агенту вопрос с названием сценария и номером t-шага.
