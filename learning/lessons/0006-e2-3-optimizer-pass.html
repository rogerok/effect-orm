Урок 0006 · E2.3 · 15–25 минут

Оптимизируй дерево снизу вверх

Твоя цель — не написать ещё один SQL-компилятор, а выполнить чистую свёртку (fold), которая получает Predicate AST и возвращает эквивалентный, более простой AST.

Конкретный результат

После урока ты сможешь реализовать src/compiler/optimizer.ts и объяснить путь одного вложенного предиката:

And(Not(Not(Gt(Column("age"), Literal(18)))))

          рекурсивный проход
                  ↓

Gt(Column("age"), Literal(18))

Это напрямую продолжает миссию: тот же свободный AST получает ещё один интерпретатор. Compiler сворачивает дерево в SQL, optimizer сворачивает его в другое дерево.

Сначала найди разрыв в условии

В текущем src/compiler/ir.ts типы разделены:

Expr      = Column | Literal
Predicate = Eq | Gt | … | And | Or | Not | Between

Но текст E2.3 требует Eq(lit(x), lit(y)) → lit(x === y). Это невозможно типизировать как Predicate → Predicate: Literal не является Predicate. Ни as Predicate, ни any проблему модели не исправят.

Acceptance-пример уточняет контракт иначе: равные литералы должны дать null, а optimizeSelect должен превратить результат пустого And() в where === undefined. Для этой реализации используем Predicate | null, где null — внутреннее служебное значение (sentinel) «истинный фильтр можно убрать».

null здесь не означает SQL NULL. Это выбранный результат функции оптимизации.

undefined здесь означает отсутствие свойства. В tsconfig.json включён exactOptionalPropertyTypes, поэтому where?: Predicate не разрешает присвоить where: undefined. Когда фильтр исчезает, верни копию SelectIR без ключа where; не ослабляй тип ради оптимизатора.

Главная механика: дети до родителя

Локальное правило должно видеть уже оптимизированных детей. Иначе внешний And не узнает, что вложенный Not(Not(p)) уже стал одним p.

Прогноз порядка обхода

В каком порядке должен работать каждый рекурсивный вариант?

Сделай прогноз до чтения следующего блока.

Модель прохода — намеренно не готовая реализация:

visit(node):
  optimizedChildren = visit(each child)
  rebuiltNode = rebuild(node, optimizedChildren)
  return applyLocalRule(rebuiltNode)

TypeScript сузит вариант объединения после проверки _tag; это стандартный narrowing для discriminated union.

Переведи правила в наблюдаемые контракты

And()
Возвращает служебное значение. На границе SelectIR.where оно превращается в undefined.
And(p)
Возвращает оптимизированный p, не исходную оболочку.
Not(Not(p))
Возвращает оптимизированный внутренний p.
Eq(lit, lit)
Для равных примитивных значений, кроме null (non-null primitives), возвращает служебное значение; ложную константу текущий компилятор уже умеет выражать пустым Or(), который компилируется в FALSE.
Or(p, p)
Возвращает один оптимизированный p. Для начала считай дублем именно один и тот же переданный AST-узел.
остальные варианты
Сохраняют свой тег и данные; рекурсивные поля содержат оптимизированных детей.

Почему нельзя начать с одного огромного switch. У тебя две разные обязанности: рекурсивно нормализовать детей и применить локальное правило алгебры (algebraic rule). Если смешать их, легко оптимизировать корень, но пропустить глубоко вложенный узел. Сначала держи в голове эти два шага, даже если в итоговом коде они находятся в одной ветке.

Твоя реализация: четыре коротких шага

  1. Красный контрактСоздай optimizer.test.ts и зафиксируй пять правил плюс один вложенный вариант.
  2. СигнатурыОпредели выход прохода по предикату и переход «служебное значение → необязательный WHERE».
  3. СвёрткаРазбери каждый _tag исчерпывающе; сначала дети, затем правило узла.
  4. ЧистотаПроверь, что входной AST не изменился, а Select пересобран через копию.

Минимальный набор тестов

  1. And(inner) → inner.
  2. And() → null.
  3. Not(Not(inner)) → inner.
  4. Eq(Literal(1), Literal(1)) → null.
  5. Or(inner, inner) → inner.
  6. And(Not(Not(inner))) → inner — этот case доказывает рекурсивность.
  7. optimizeSelect({...ir, where: And()}).where → undefined.

Для проверки отсутствия мутации сделай снимок входа до вызова и сравни его после. Не требуй, чтобы каждый неизменившийся листовой узел имел новую ссылку: неизменяемое переиспользование структуры (immutable structural sharing) не является мутацией.

Подсказка 1 — только границы функций

Одна функция принимает Predicate и допускает служебное значение в результате. Вторая принимает SelectIR, вызывает первую только при наличии where и возвращает новый SelectIR.

Подсказка 2 — где искать существующий стиль

Посмотри на исчерпывающий Match.value(...).pipe(..., Match.exhaustive) в src/compiler/compiler.ts. Переиспользуй стиль разбора union, но не копируй SQL-логику: выход optimizer — AST.

Ограничение, которое нельзя забыть

PostgreSQL использует трёхзначную логику. В частности, NULL = NULL даёт UNKNOWN, а в JavaScript null === null даёт true. Поэтому правило курса с === сейчас применяй только к примитивным литералам, кроме null, которые закреплены тестом. Не расширяй его молча на весь unknown.
