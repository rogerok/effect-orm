Знакомая аналогия

Во фронтенде ты уже встречал деревья:

<main>
  <section>
    <button>Сохранить</button>
  </section>
</main>

DOM состоит из узлов: у main есть ребёнок section, у него — button. AST устроен так же, только узлы — обычные JavaScript-объекты, а не HTML-элементы.

Один узел из проекта

В src/compiler/ir.ts отрицание условия описано так:

{
  readonly _tag: "Not";
  readonly pred: Predicate;
}
  • _tag: "Not" означает «этот объект — отрицание».
  • pred содержит другое условие, то есть дочерний узел.
  • Никакого SQL и обращения к базе здесь ещё нет. Это только данные.

Ментальная замена: когда видишь «AST-узел», читай «объект с полем _tag и возможными вложенными объектами».

Что делает оптимизатор

Оптимизатор получает один объект и возвращает более простой объект с тем же смыслом. Первое правило E2.3:

Not(Not(p))  →  p

Пример входных данных:

const input = {
  _tag: "Not",
  pred: {
    _tag: "Not",
    pred: p
  }
};

Внешний Not содержит внутренний Not. Внутренний Not содержит p. Поэтому результатом будет именно p.

Где появляется рекурсия

Представь более глубокое дерево:

And(
  Not(Not(p))
)

Сначала нужно обработать ребёнка Not(Not(p)) и получить p. Только затем внешний And увидит, что у него остался один ребёнок. Поэтому функция обработки вызывает саму себя для вложенных Predicate. Это и есть рекурсия.

Псевдокод без TypeScript-синтаксиса:

обработать(узел):
  если у узла есть дети:
    сначала обработать детей
  затем упростить сам узел
  вернуть результат
