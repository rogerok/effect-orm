Когда сравнение уже известно

Научиться сворачивать Eq(lit(x), lit(y)), не перепутав выражение, предикат и отсутствие WHERE.

← Карта обучения · ← Урок E2.3 · Справочник оптимизатора · Запись результата

Что уже работает

Текущий optimizePredicate рекурсивно обрабатывает детей многосоставного And, удаляет пустой And(), разворачивает And(p) и снимает двойной Not. Следующая граница — constant folding, вычисление результата операции над двумя литералами заранее.

Сначала проверь контракт типов

В текущем ir.ts два множества узлов разделены:

Expr      = Column | Literal
Predicate = Eq | Gt | ... | And | Or | Not

optimizePredicate(input: Predicate): Predicate | null

lit(true) создаёт Expr. Функция обязана вернуть Predicate | null. Поэтому буквальное правило из текста задания

Eq(lit(x), lit(y)) → lit(x === y)

не помещается в тип текущего AST.

В условии есть расхождение. Текст просит вернуть Literal, а acceptance-тест для Eq(lit(1), lit(1)) ожидает null. Такой тест фиксирует выбранный контракт, но не доказывает, что контракт удачен: тест тоже может быть ошибочным или описывать только один частный контекст.

Почему null означает TRUE

Компилятор превращает пустой And() в SQL TRUE. Оптимизатор превращает тот же узел в null. Когда позже optimizeSelect положит это значение в optional-поле where?, null должно стать undefined: запрос без WHERE пропускает все строки, как WHERE TRUE.

Eq(Literal(1), Literal(1))
             ↓  1 === 1
            true
             ↓  контракт optimizer
            null
             ↓  граница SelectIR.where?
         where: undefined

null безопасен не везде. Если он означает постоянный TRUE, то внутри And его можно отбросить: p AND TRUE = p. Внутри Or отбросить его нельзя: p OR TRUE = TRUE. Под Not он должен превратиться в FALSE. Следовательно, null — не просто «узла больше нет», а скрытое логическое значение, которое каждый родитель обязан трактовать по-разному.

Прогноз до правки

Что должен вернуть текущий API для eq(lit(1), lit(1))?

Сначала выбери ответ.

Одна пользовательская правка

Не добавляй пока весь Eq и Or. Сделай один красно-зелёный цикл:

  1. В optimize.test.ts добавь acceptance-сценарий eq(lit(1), lit(1)) → null.
  2. Запусти только этот файл и убедись, что новый тест сначала падает.
  3. Добавь в optimizePredicate ветку, которая входит только в Eq с двумя Literal.
  4. Внутри ветки вычисли строгую эквивалентность значений. Для результата true верни значение, предсказанное выше. Ветку false пока оставь без нового преобразования.
  5. Снова запусти только тесты оптимизатора.

Каркас намеренно неполный — условия narrowing и возврат пишет пользователь:

если корень — Eq
  и left — Literal
  и right — Literal:
    equal = left.value === right.value
    если equal:
      вернуть представление TRUE

вернуть исходный узел

Почему пока не сворачиваем любые значения

Literal.value имеет тип unknown. JavaScript === и SQL = не равнозначны на всём этом множестве. Например, в JavaScript null === null даёт true, а обычное SQL-сравнение NULL = NULL даёт NULL, то есть «неизвестно». PostgreSQL описывает это прямо в разделе Comparison Functions and Operators. Сам оператор === определён алгоритмом ECMAScript IsStrictlyEqual.

Для учебного acceptance-сценария с числами правило однозначно. Перед общим правилом понадобится отдельно решить допустимый домен литералов и представление постоянного FALSE.

Инвариант шага: оптимизатор может менять форму дерева, но не множество строк, которое пропускает предикат.

Первичные источники

  • ECMAScript: IsStrictlyEqual — точная семантика ===.
  • PostgreSQL: Comparison Functions and Operators — поведение = и NULL.
  • PostgreSQL: Logical Operators — таблицы истинности AND, OR, NOT.
После зелёного теста пришли свою ветку Eq или ошибку TypeScript. Задавай любые уточняющие вопросы: следующий шаг зависит от того, как ты объяснишь представление постоянного FALSE.
