Выполнить ≠ зафиксировать

Три состояния записи и точное разделение ответственности в текущем проекте.

Интерактивный урок · Словарь · withTransaction · Savepoint · Ограничения

Краткий словарь

Эффект (Effect)
Описание вычисления. Создание эффекта не означает его исполнение. В выполняющемся Effect.gen выражение yield* effect исполняет вложенный эффект.
Транзакция
Механизм БД для согласованной фиксации группы изменений. Для этого урока ключевая гарантия — атомарность: всё или ничего.
BEGIN
Начало явной транзакции. Следующие запросы на том же соединении участвуют в ней.
RETURNING
Результат исполненного запроса записи. Может содержать созданный БД ключ до фиксации транзакции.
COMMIT
Фиксация транзакции. Успешное завершение внутреннего savepoint этого не заменяет.
ROLLBACK
Отмена изменений текущей транзакции. Не отменяет отправленное письмо, HTTP-запрос или изменение JavaScript-объекта.
Unit of Work
Шаблон учёта изменений и организации их сохранения. В проекте реализован как очередь эффектов, а не автоматическое отслеживание изменений сущностей.
Отложенная запись
(write-behind)
Запросы записи исполняются позже регистрации. В отличие от неё, обычная транзакция может исполнять SQL сразу, откладывая только фиксацию.
Точка сохранения
(savepoint)
Метка внутри транзакции. Позволяет отменить последующие изменения, не отменяя предшествующие.

Источники: PostgreSQL: Transactions, RETURNING, Fowler: Unit of Work, Effect: generators.

Как читать свой withTransaction

Файл: src/uow/transaction.ts. Ниже — поведение текущей реализации, а не обязательный интерфейс всех библиотек.

  1. Создаётся новый эффект. Вызов функции ещё не открывает транзакцию. При исполнении эффект получает Driver и значение TransactionDepth.
  2. Выбирается граница. Глубина 0 означает отсутствие внешней обёртки в текущем контексте. Используется BEGIN. При большей глубине используется SAVEPOINT.
  3. Исполняется переданный эффект. Внешняя обёртка предоставляет ему глубину 1, вложенная — depth + 1. provideService задаёт значение для вложенного вычисления, а не меняет глобальный счётчик.
  4. Проверяется Exit. Exit.isSuccess проверяет исход всей переданной операции. При успехе — COMMIT или RELEASE SAVEPOINT. При неуспехе — ROLLBACK или ROLLBACK TO SAVEPOINT.
  5. Возвращается результат. Тип результата A сохраняется. Ошибка завершающего действия не позволяет считать всю обёртку успешной.

Зачем acquireUseRelease

acquire начинает транзакцию, use исполняет операцию, release завершает транзакцию по её исходу. Если начало удалось, Effect выполняет завершающую часть при завершении основной — в том числе при ошибке или прерывании. Начало и завершение защищены от прерывания средствами Effect. Это не гарантия при уничтожении процесса или потере питания.

Effect.as(undefined) отбрасывает результат команды начала. Аргумент _ в release — неиспользуемый результат начала. Аргумент exit описывает исход основной операции.

Effect.orDie на верхнеуровневых COMMIT и ROLLBACK переводит ошибку драйвера в дефект. Ошибка не исчезает, но перестаёт быть обычной типизированной ошибкой канала E.

Точный контракт RC: Effect 4.0.0-rc.108: acquireUseRelease, provideService, orDie.

Что делает UoW вокруг обёртки

register A, register B             — только очередь
uow.commit
  → прочитать очередь
  → withTransaction
      BEGIN
      исполнить A
      исполнить B
      COMMIT
  → очистить очередь

При ошибке операции withTransaction выполняет SQL ROLLBACK. В текущем UoW очередь остаётся, потому что последующая очистка не исполнилась. Явный uow.rollback отбрасывает очередь и очищает его Identity Map. Он сам SQL не выполняет.

При пустой очереди uow.commit не открывает транзакцию. При успехе отдельные результаты отбрасываются из-за discard: true. Источник: unit-of-work.ts.

Вложенность: это не второй независимый COMMIT

Внешняя операция уже открыла транзакцию. Внутренняя тоже использует withTransaction. Она видит ненулевую глубину и создаёт savepoint. 

BEGIN                        — внешняя обёртка
  запись A
  SAVEPOINT inner            — внутренняя обёртка
    запись B
  RELEASE SAVEPOINT inner    — внутренний успех
ROLLBACK                     — поздняя внешняя ошибка

Итог: отменены и A, и B.

RELEASE SAVEPOINT завершает внутренний участок, но не фиксирует внешнюю транзакцию. Поэтому вложенный uow.commit тоже не обещает окончательной фиксации до внешнего COMMIT. 

BEGIN
  запись A
  SAVEPOINT inner
    запись B → ошибка
  ROLLBACK TO SAVEPOINT inner
  внешняя операция обработала ошибку
  запись C
COMMIT

Итог: A и C сохранены; B не сохранена.

Если внешняя операция не обработает внутреннюю ошибку, ошибка дойдёт до внешней обёртки и вызовет полный ROLLBACK. После ROLLBACK TO сама точка сохранения остаётся определённой; наружная транзакция ещё открыта.

Источник: раздел Savepoints в PostgreSQL: Transactions.

Как выбрать границу

Создать пользователя и пост с его ключом: обычный Repository внутри общего withTransaction. Первая вставка возвращает id, вторая использует его. Откат остаётся возможным до общего COMMIT.

Накопить заранее подготовленные записи: UoW. Исполняющий эффекты UoW сам использует транзакцию. Отдельно оборачивать каждый метод репозитория недостаточно для общей атомарности нескольких вызовов.

В PostgreSQL даже без явного BEGIN отдельный SQL-запрос выполняется в неявной транзакции. Явная транзакция приложения нужна, чтобы задать общую границу нескольким запросам; она не обязательна для каждого HTTP-запроса.

Чего текущий код не обещает

  • Обработка ошибки внутри: если основная операция превращает ошибку в успешный результат, обёртка увидит успех. Это ещё не гарантирует успешный COMMIT: после SQL-ошибки PostgreSQL может находиться в аварийном состоянии транзакции. В тесте ошибки Effect.result(uow.commit) стоит снаружи обёртки.
  • Соединение: все SQL-команды транзакции должны выполняться на одном соединении без вмешательства чужой операции. TransactionDepth сам не резервирует соединение в пуле и не блокирует другие fibers.
  • Память: SQL ROLLBACK не очищает Identity Map и не восстанавливает JavaScript-объекты. Карта репозитория пока не подключена к карте UoW.
  • Очередь: текущий UoW рассчитан на последовательное использование. Конкурентные commit/register/rollback не синхронизированы. После вложенного commit очередь уже очищена, даже если внешняя транзакция позже откатится.
  • Производительность: одна транзакция не означает один запрос или один сетевой обмен.

Эти ограничения следуют из transaction.ts, unit-of-work.ts и make-repository.ts. Это учебная реализация, не утверждение о готовности к конкурентной production-нагрузке.
