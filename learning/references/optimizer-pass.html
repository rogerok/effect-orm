Контракт текущего проекта

Вход
Predicate из src/compiler/ir.ts.
Выход
Predicate. Постоянные результаты представлены узлом Boolean, чтобы тип результата оставался в AST.
Проход по statement
optimizeSelect удаляет свойство where только для Boolean(true); ложное условие остаётся и компилируется в WHERE FALSE.
Чистота
Вход не меняется. Допустимо переиспользовать неизменившиеся readonly-узлы; запрещены push, присваивания полям входа и изменение входных массивов.

Не записывай where: undefined. При exactOptionalPropertyTypes: true свойство where?: Predicate должно либо отсутствовать, либо содержать Predicate. Для результата без фильтра пересобери SelectIR без ключа where.

В источнике есть противоречие. Текст E2.3 требует Eq(lit(x), lit(y)) → lit(x === y), но Literal входит в Expr, а не в Predicate. Текущий проект решает эту границу отдельным Predicate-узлом Boolean; acceptance-пример курса ожидает старый контракт с null.

Порядок обхода

  1. Разобрать тег_tag определяет форму и дочерние узлы.
  2. Обойти детейСначала нормализовать вложенные предикаты.
  3. ПересобратьСоздать узел из уже нормализованных детей.
  4. Свернуть локальноПрименить правило текущего тега.

Такой обход после детей (post-order traversal) позволяет одному внешнему правилу увидеть уже упрощённый внутренний AST.

Константы без изменения IR

Текущий compiler уже задаёт две канонические формы:

  • Boolean(true) компилируется в TRUE; на верхней границе его можно заменить отсутствующим WHERE.
  • Boolean(false) компилируется в FALSE; его нельзя заменять отсутствием WHERE.

Явный Boolean сохраняет константу внутри Predicate и делает рекурсивные правила композиционными: в And истинный ребёнок удаляется, а в Or истинный ребёнок завершает весь результат.

Равенство для дедупликации

  • Минимальный контракт курса: два аргумента — один и тот же объект p. Тогда достаточно тождественности ссылок (reference identity).
  • Расширенный контракт: отдельно созданные, но одинаковые деревья тоже считаются дублями. Тогда нужно явное структурное равенство AST (AST-specific structural equality).
  • Не использовать вслепую: JSON.stringify. Значение Literal.value имеет тип unknown; BigInt, undefined, порядок ключей и циклические объекты делают сериализацию ненадёжным определением равенства.

Граница корректности SQL

SQL использует трёхзначную логику: кроме TRUE и FALSE существует UNKNOWN. PostgreSQL прямо показывает, что NULL = NULL даёт UNKNOWN, хотя JavaScript-выражение null === null даёт true. Поэтому свёртка констант (constant folding) через JS === безопасна только для домена литералов, который упражнение явно ограничивает. Для E2.3 достаточно примитивных тестовых значений, кроме null; расширение домена требует отдельной семантики.
