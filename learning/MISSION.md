# Mission: Потоковый full table scan для E2.7

## Why

Самостоятельно реализовать упражнение E2.7: провести миллион строк через типизированный `Stream`, вычислить агрегат без материализации всего результата и честно измерить потребление памяти. Цель — понимать, почему ограниченная память зависит не от слова `Stream`, а от всей цепочки producer → adapter → consumer.

## Success looks like

- Объяснить разницу между `Effect<ReadonlyArray<Row>>` и `Stream<Row>` и найти скрытую материализацию массива.
- Задать typed adapter `Select<R> → Stream<R, DriverError, Driver>`, который компилирует запрос и делегирует потоковому методу драйвера.
- Выполнить full table scan через `selectAll` и `Stream.runFold`, удерживая аккумулятор фиксированного размера.
- Получить точные `count` и `sum` для миллиона вставленных строк.
- Сравнить потоковый fold с материализацией результата и интерпретировать `heapUsed`, `external` и `rss`, не выдавая snapshot до/после за измерение пика.
- Объяснить, когда iterator/cursor должен закрыться при успехе, ошибке и прерывании.

## Constraints

- Главные источники: сохранённая глава, публичный API и исходники установленного `effect@4.0.0-rc.108`, документация Node.js.
- Сначала диагностировать ментальную модель; маршрут строить только по обнаруженным пробелам.
- Backend-код, тест и memory experiment пишет пользователь; преподаватель даёт модель, задания и обратную связь.
- Чередовать объяснение, прогноз, самостоятельную правку и наблюдаемую проверку.
- Учитывать текущее состояние проекта: `executeStream` уже есть у SQLite и PGlite; fluent builder из урока 3 ещё не реализован.

## Out of scope

- Fluent phantom-typed builder урока 3.
- Реализация потокового API для отдельной интеграции libSQL.
- Универсальные cursor abstractions, Repository, Unit of Work и упражнения E2.8+.
- Production benchmark framework и оптимизация драйверов вне контракта E2.7.
