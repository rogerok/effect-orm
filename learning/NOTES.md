# Teaching notes

- Пользователь хочет сначала пройти диагностику ментальной модели, а учебный маршрут строить только по обнаруженным пробелам.
- Чередовать объяснение своими словами, прогноз поведения, чтение существующего кода, небольшую пользовательскую правку и проверку типами/тестами.
- После установления базовой модели не дробить знакомый TypeScript-синтаксис на отдельные вопросы. Пользователь прямо отметил вопрос про union return type как слишком простой; повышать сложность через вложенные деревья и контрпримеры, которые меняют поведение.
- Главный критерий уверенности: пользователь может без копирования заново собрать путь `алгебра → AST → smart constructors → compiler → Effect.run`.
- До завершения этой миссии не использовать материал раздела 2.6 и далее.

- Предыдущая миссия исключает раздел 2.6, тогда как E2.4 требует typed wrapper. `MISSION.md` пока не менять: согласовать расширение границ перед обновлением миссии.

### Диагностика типизированного Between

- Пользователь самостоятельно заметил необязательность бренда и возможность расширить тип `Expr<T>`; предположил, что смешанный вызов может дойти до ошибки в БД. Это основание не повторять вводную про generics, но отдельно разобрать совместимость типов и вывод `T`.
- Изолированный запуск установленного `tsc` показал: при `age: Expr<number>` вызов `between(age, lit(18), lit('65'))` отклоняется с TS2379. Явный `<number | string>`, первый аргумент `Expr<number | string>` и raw IR-вызов принимаются. Объект `{ _tag: 'Literal', value: '65' }` также присваивается `Expr<number>` без бренда. Временные файлы удалены; backend не менялся.
- Проверка в изолированной PGlite: `SELECT 40::integer BETWEEN $1 AND $2 AS matches` с `[18, '65']` вернула `true`. Строковый параметр не гарантирует ошибку БД: в данном контексте он принят как число.
- Диагностический ответ: пользователь верно предсказал отклонение вызова `between(Expr<number>, Expr<string>, Expr<string>)`, но объяснил его через `_tag`. Это обнаруженный пробел, не подтверждённое понимание фантомного маркера.
- Подготовлен [урок 0009](lessons/0009-expression-tag-versus-value-type.html) и [памятка](references/expression-type-marker.html): `_tag` различает форму узла, `[Brand]?: T` сохраняет тип значения. Следующий прогноз — останется ли ошибка, если мысленно убрать маркер и оставить `type Expr<T> = ExprIR`. Исправление модели пока не подтверждено ответом; новую запись об освоении не создавать.

## Текущий запрос: подготовка к E2.5

- Цель пользователя — самостоятельно выполнить **упражнение E2.5**, не раздел 2.5: `compileCache` через `Effect.cached`, структурный хеш IR, замер ускорения на 10 000 одинаковых запросов.
- Не повторять освоенный рекурсивный обход и нормализацию из E2.3. Понимание фантомного маркера из урока 0009 пока не подтверждено, но это не обязательная предпосылка кеширования нетипизированного IR.
- В `src/compiler/run.ts` компиляция пока вызывается напрямую. `compile(ir, dialect)` возвращает и SQL, и параметры; пользователь подтвердил, что переиспользование зависит от содержимого IR, включая литералы, и диалекта.
- Прочитаны точные исходники Effect 4.0.0-rc.108. Изолированный запуск через `pnpm exec node --input-type=module` подтвердил ленивое выполнение `Effect.cached`, повторное использование результата одного кешированного эффекта и одинаковые хеши разных объектов `{ _tag: 'Literal', value: 18 }`.
- Диагностика A/B/C завершена: новый объект с прежним содержимым допускает переиспользование, другой литерал или диалект — нет. Подтверждение записано в [0016](records/0016-compiled-cache-reuse-boundary.md).
- Подготовлен [урок 0010](lessons/0010-cached-effect-lifetime.html) и [памятка](references/cached-effect-lifetime.html): внешний эффект создаёт кеш, внутренний использует его. Изолированный эксперимент подтвердил независимость двух кешей, созданных исполнением одного внешнего эффекта.
- После уточнения «сохранять нужно memo, не только IR» пользователь верно предсказал новый кеш при каждом исполнении makeCached. Узкая подтверждённая граница записана в [0017](records/0017-cached-allocation-versus-reuse.md); самостоятельный поиск записей ещё не проверен.
- Пользователь верно назвал последствие коллизии в Map<number, memo>: результат другого запроса. Подтверждение — [0018](records/0018-hash-collision-is-not-equality.md).
- Следующий шаг — поиск по IR через Effect HashMap, где хеширование и сравнение ключей уже реализованы, вместо самописной обработки коллизий. На rc.108 изолированно проверено: новый объект с прежним содержимым находится в HashMap, но не в JavaScript Map; другой литерал не находится. Не путать с MutableHashMap, у которого иной контракт обычных объектов.
- Затем — неизменяемость ключей и обновление неизменяемой коллекции, связывание поиска с memo и замер 10 000 обращений с учётом стоимости поиска. Владение этими механизмами пользователем ещё не проверено.
- Пользователь попросил двигаться дальше, не прислав фрагмент с HashMap. Не считать операции коллекции, Option и её неизменяемость освоенными. Следующее объяснение связывает поиск записи с ленивой компиляцией: состояние коллекции живёт между обращениями, запись содержит memo, а compile откладывается через Effect.sync.
- Пользователь написал синхронную фабрику в src/compiler/compiler.ts. После объяснения неизменяемости исправил const map на let и сохранил результат HashMap.set обратно в map. Изолированная проверка текущей фабрики: четыре обращения (18, 18 новым объектом, 21, 18 новым объектом), две компиляции, правильные параметры. Результат — [0019](records/0019-synchronous-compile-cache-reuse.md).
- Пользователю непривычно переприсваивание map: объяснить разницу между изменяемой переменной, хранящей текущую версию, и неизменяемой коллекцией. Дальше — хранение memo вместо Compiled; это требование E2.5 ещё не реализовано.
- При переходе к Effect пользователь обернул фабрику во внешний Effect.gen, но внутренний compileCache оставил синхронным: он возвращает Compiled, напрямую вызывает compile и сохраняет готовый результат. Добавленные work и makeCached не исполняются. Изолированный запуск подтвердил: запуск фабрики не компилирует, вызов возвращённой функции сразу компилирует и отдаёт не Effect.
- Пользователь снова сообщил, что не понимает. Снизить размер шага: сначала различить эффект создания фабрики и эффект обработки одного IR; добиться ленивого вызова compileCache(ir), затем отдельно получать memo и сохранять его. Предыдущий прогноз про новый кеш не считать доказательством владения всей цепочкой.
- Пользователь перенёс Effect.gen во внутреннюю compileCache, оставив map во внешней фабрике. Проверка подтвердила ленивость и переиспользование: 0 компиляций при создании эффекта, 1 при первом исполнении, 1 суммарно после повторного структурно равного IR. Подтверждение — [0020](records/0020-lazy-compile-cache-request.md).
- Следующий узкий шаг: убрать прямой вызов compile и лишний placeholder; получить memo исполнением makeCached, затем получить Compiled исполнением memo. Пока можно сохранять Compiled, чтобы отдельно проверить два уровня Effect; после этого заменить значение записи на memo и согласовать ветки попадания и промаха.
- Пользователь заменил прямую компиляцию на два yield*: `makeCached = yield* Effect.cached(work)`, затем `memo = yield* makeCached`. Цепочка исполняется корректно, но имена сдвинуты: makeCached содержит кешированный эффект, memo — готовый Compiled. Коллекция по-прежнему HashMap<IR, Compiled>.
- Проверка текущей фабрики: создание эффекта ленивое, четыре исполнения с литералами 18, 18, 21, 18 вызвали compile дважды; параметры правильные. Следующий шаг — сохранять именно кешированный эффект, а в обеих ветках выдавать результат его исполнения. Не объявлять понимание двух уровней подтверждённым только по работающему коду.
- Пользователь почти верно пересказал модель: на попадании берём memo из map, исполняем и возвращаем результат. Уточнена одна формулировка: кешируется содержимое IR, а не отдельный вызов; одна запись на один IR, а поиск идёт до создания записи. Модель заявлена, но самостоятельная демонстрация ещё не проверена.
- Пользователь вынес makeCompileCache в src/compiler/compile-cache.ts и написал бенчмарк compile-cache.bench.ts. Первый замер дал speedup 0.085; разложение цикла показало, что это честный результат: поиск со свежим ключом ~5.2 мс против компиляции 1.4 мс на обращение. Подтверждение — [0021](records/0021-structural-lookup-costs-more-than-compile.md).
- В бенчмарке не хватало прогрева, N был 1000, а сценарий с одним объектом отсутствовал. Пользователь явно отключил режим наставника на эту сессию и попросил записать бенчмарк за него. Файл compile-cache.bench.ts переписан преподавателем: N = 10_000, прогрев 200, сценарии freshTrees и sameObject с раздельным speedup. check-types прошёл.

Для E2.5 остался acceptance-тест контракта (toBe на повторном объекте, параметры для разных литералов) — после отключения наставника это может сделать преподаватель, если пользователь попросит.
