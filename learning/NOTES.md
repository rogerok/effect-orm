# Teaching notes

Рабочие правила и незакрытые долги. История результатов лежит в [записях](records/index.md); здесь она не дублируется.
Файл переработан 2026-09-08: хронология занятий E2.3–E2.7 удалена, из неё оставлены только правила, действующие сейчас.

## Как учить этого пользователя

- Сначала диагностика ментальной модели, маршрут — по обнаруженным пробелам. Не преподавать заново то, что подтверждено
  записью.
- Порядок объяснения: literal-пример с наблюдаемым выводом → формулировка выбора → задача → узкая проверка. Вопрос о
  design tradeoff задавать только после того, как различие показано на конкретных значениях.
- Не дробить знакомый TypeScript-синтаксис на отдельные вопросы. Сложность повышать вложенными структурами и
  контрпримерами, которые меняют поведение.
- Не вводить собственных названий для рабочих приёмов. Писать, что именно происходит: какой файл создаётся, чем
  запускается, когда удаляется. Слово «зонд» из старых записей заменено на «временный проверочный скрипт».
- После двух неудачных попыток на одном уровне переходить к показанному коду. Формулировка правила есть в `AGENTS.md`.
- Скелет с пропусками пользователь не заполняет: на шаге L3.21 он дважды спросил, что писать вместо плейсхолдеров.
  Когда от задачи осталась только транскрипция уже названного решения, показывать строку целиком и переносить нагрузку
  на проверку (мутацию, прогноз, объяснение), а не на набор текста.
- Пользователь — фронтенд-разработчик без предыдущего опыта с ORM, компиляторами и SQL. Базовый SQL объяснять на
  наблюдаемых данных, а не термином.
- В L3.26 пользователь неоднократно просил «давай дальше» после предложения одной и той же мутации.
  Не повторять это задание как единственный способ продолжения; сохранить непроверенное отдельно от подтверждённого.
  Результат и независимость запросов уже наблюдались на реальной SQLite; мутацию не считать выполненной.
- На L3.27 пользователь попросил перейти к DELETE и отложить тесты. Давать законченный построитель одним шагом,
  не требовать теста после каждого метода. После DELETE провести один общий этап проверки UPDATE и DELETE;
  отличать подтверждение временным сценарием от постоянной защиты от регрессий.
- На L3.28 объяснение параметров типа статического метода оказалось слишком резким переходом к новой концепции.
  Сначала показывать различие вызовов на объекте и на классе. Не говорить, что `R` хранится в экземпляре:
  параметр типа существует только при проверке типов. Исправление с помощью не считать самостоятельным пониманием.
- На E3.4 пользователь явно отложил постоянные тесты и разрешил дальнейшую проверку временными сценариями.
  Не требовать написания тестов как немедленного условия продолжения; сохранять отложенные проверки отдельно.
- На E3.5 пользователь попросил небольшие итерации. Это правило отменяет прежнее указание с E3.27–E3.28
  «давать законченный построитель одним шагом». Один шаг — один наблюдаемый переход и одна узкая проверка.
  Задание из трёх правок в разных местах файла считается слишком крупным; разбивать на отдельные итерации.
- При подключении декодирования пользователь сообщил об усталости и повторно попросил
  двигаться совсем небольшими шагами. Давать одну локальную правку; не объединять
  подготовку кодеков, обход строк, NULL и обработку ошибок в одно задание.
- На L3.29 после серии маленьких правок пользователь попросил общий обзор. При продолжении
  кратко связывать текущую правку с путём «доменное значение → encode в копии IR →
  compile → Driver → SELECT decode», не заменяя обзор перечнем будущих фаз.
- Пример с исполнением одного INSERT на разных БД вызвал путаницу. Пользователь верно
  понимает, что конкретное исполнение получает один Driver из предоставленного Layer.
  Момент выбора кодека объяснять через доступность Driver при исполнении Effect,
  а не через необходимость менять диалект одной базы.
- При изменении типов JSON пользователь снова спросил «зачем мы это делаем». Перед следующим
  шагом кратко напоминать цель: публичный API принимает и возвращает доменные значения,
  а кодек преобразует представление для базы. Не превращать занятие в последовательность
  правок без видимого результата.
- Пользователь просил лёгкие наводящие вопросы и более простые объяснения. Задавать один
  вопрос на конкретном примере. Различие `unknown`/`never` объяснялось через boolean-кодек
  и кодек дат; ответ «нельзя передать true неизвестному из двух кодеков» подтверждён,
  самостоятельный вывод общей модели типов не подтверждён.
- При обсуждении локальных приведений сразу обозначать ограничение: после потери связи
  значения с кодеком в IR исполнитель доверяет метаданным. `AnyCodec` не восстанавливает
  эту связь и не является runtime-валидацией. Не обещать полную типобезопасность.
- Проверка round-trip должна писать через публичный API ORM. Сырой SQL полезен для независимого
  контроля хранения и для подготовки некорректных данных в тестах декодирования.
- Для `RETURNING` проверять непосредственный результат `save`/INSERT, а не заменять его

- На занятии по UoW пользователь уточнил уровень помощи: одной цели без опоры недостаточно, но готовые выражения и
  подробный алгоритм избыточны. Давать цель, нужные инструменты, пример из существующего проекта и небольшой участок
  самостоятельной работы. Backend-код по-прежнему пишет пользователь.

## Локальная цель: транзакции и Unit of Work

По явному запросу пользователя разбираем различие регистрации, исполнения SQL и фиксации транзакции, чтобы осознанно
выбрать контракт собственного Repository. Опора — [урок 0014](lessons/0014-transactions-and-unit-of-work.html)
и [памятка](references/transactions-and-uow.html). HTTP-интеграция E4.7 пока необязательна.
Исторический `MISSION.md` описывает начало урока 3; глобальная миссия без отдельного согласования не переписана.
Подтверждены пользовательские тесты отложенной записи и атомарного отката. Самостоятельное объяснение различия
транзакции и UoW ещё не подтверждено; чтение урока или прохождение агентом виджета не считать пониманием пользователя.

## Правила проверки

- Новый тест проверять мутацией проверяемого кода. Зелёный тест доказывает только то, что он умеет проверять.
- Приведение типа ставить на минимальное значение, которое действительно не выводится, а не на весь возвращаемый
  объект: `as unknown as` на объекте целиком трижды скрыл ошибку формы результата.
- Молчание линтера не является доказательством осмысленности кода.
- Проверка `length` не сужает тип элемента при `noUncheckedIndexedAccess`; сужает только сравнение значения с
  `undefined`.
- Матчеры проекта живут в `src/config/result-matchers.ts` и подключены через `setupFiles`; `expect` доступен глобально
  из-за `globals: true` в `vitest.config.ts`. Поля ошибки проверять через `expectFailure` и `toMatchObject`:
  `toEqualFailure` сравнивает объекты целиком и расходится по `stack`.

## Команды, проверенные в этом проекте

- Запуск исходников без сборки: `node --conditions=development --import tsx <файл>`. Без `--conditions=development`
  package import map выбирает `./dist/*`, которого нет.
- Узкая проверка типов: `pnpm check-types`. Узкий тест: `pnpm test <путь>`.
- Утверждения `expectTypeOf` проверяет только `pnpm check-types`. В `vitest.config.ts` нет блока `typecheck`, поэтому
  во время исполнения `expectTypeOf` не делает ничего и `pnpm test` показывает passed при любых типах. Включение
  `typecheck.enabled` само по себе не поможет: `typecheck.include` в `vitest@4.1.11` равен
  `['**/*.{test,spec}-d.?(c|m)[jt]s?(x)']`, то есть файлы `*.test.ts` под шаблон не подпадают.

## Эталон курса и осознанные расхождения

- Полный текст курса лежит вне репозитория:
  `~/Documents/bat-school/orm/BatSchool · Своя ORM на TypeScript + Effect.ts.html`. Разделы 3.5 и 3.6 содержат

- Правило: сверяться с разделом 3.x курса, но проверять эталон против tsconfig проекта и уже существующих модулей.

## Открытые долги

- Тестов на join во время исполнения в репозитории нет. `src/hw/e3-2.test.ts` проверяет только типы; проверки INNER и
  LEFT JOIN на реальной базе выполнялись временными скриптами и удалены.
- В `src/query/expression-builder.ts` остались неиспользуемые импорты `ColumnDef`, `SqlType` и `TableDef` — остатки
  перехода на `AnyTableDef`.
- В `src/query/builder.test.ts` остались неиспользуемые импорты `Result` и `TooManyError`.
- В `src/hw/e3-1.ts` переменная `queryLeftJoin` вызывает `innerJoin`, то есть отрицательный случай для `leftJoin` не
  покрыт; в строке 19 используется `col` из `#query/index.js` вместо `b.col`, поэтому `@ts-expect-error` может гасить
  не ту ошибку.
- Обоснование политики повторного alias пользователем не сформулировано (запись 0037). При возврате к теме спросить
  одно: какую цену платит API за отказ от запрета.
- Retrieval check по `exactOptionalPropertyTypes`: чем отличается `{}` от `{ limit: undefined }`.
- L3.23 (`executeStream` на `ExecutableUpdate`) отложен: пользователь перешёл к упражнению E3.3 сразу после E3.2.
  Зависимости у write-builder от streaming нет, но шаг остаётся долгом.
- Проверка nullability в `col` идёт через тип строки результата, а не через `expectTypeOf` на самом вызове
  `b.col(...)`. Промежуточный `Expr<T>` наблюдается только косвенно (запись 0041).
- Приём диагностики, который стоит требовать от пользователя: при `TS2536` разворачивать индексируемый тип по цепочке
  объявлений, а не править код в месте ошибки. Показан на `SourceMap`, самостоятельно не применялся.
- На L3.24 пользователь не смог предсказать результат при `Insert<{ id: number }>` и `returning: null`.
  Разобрано: параметр типа не существует при исполнении, ветку выбирает поле `returning`, а `as StatementResult<S>`
  не проверяет и не преобразует значение. Самостоятельное объяснение этой связи пока не подтверждено.
- На L3.25 пользователь предположил независимость `params` от порядка ключей любого объекта. Показано на двух
  запусках `compile`: первая строка определяет общий SQL-список колонок и порядок параметров всех строк; перестановка
  ключей последующих строк порядок параметров не меняет. Неизменным остаётся соответствие значений колонкам, а не
  сам массив параметров. Самостоятельное объяснение не подтверждено; повторную проверку отложить, не задавать
  немедленно тот же вопрос после готового разбора.
- L3.27: UPDATE проверен временными сценариями SQLite, но постоянных тестов ещё нет. После реализации DELETE
  вернуться к общим проверкам: контекст таблицы, запрет изменения PK и неверных значений, отсутствие `execute`
  до `set`, SQL/параметры, выбранные и неизменённые строки, `affectedRows`/`returning`, неизменность исходного запроса.
  Пустой `set({})` принимается типом, но компилятор не отклоняет пустой SET явно; обработка остаётся открытой.

## Границы, которые нельзя нарушать

- Backend-код, тесты, миграции и backend-конфигурацию пишет пользователь. Просьба «сделай сам» не отключает режим
  наставника: нужен явный отказ от менторства на сессию. Документация без поведения под это правило не попадает.
- Не запускать `git checkout`, `git restore`, `git stash` и другие восстанавливающие команды на файлах пользователя.
  На шаге L3.22 такая команда стёрла `src/hw/e3-2.test.ts`: файл был добавлен в индекс пустым, и восстановление из
  индекса вернуло пустую версию. Временные вставки в чужой файл убирать точечным редактированием того, что было
  добавлено, либо писать пробу в отдельный временный файл.
- Не забегать вперёд по roadmap: Repository, транзакции, relations и write builder — после текущей фазы.
