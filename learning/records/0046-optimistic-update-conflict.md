# E4.4: условное обновление не перезаписывает устаревшую версию

Пользователь с помощью реализовал обновление по первичному ключу и ожидаемой версии в одном SQL-запросе. Постоянный тест через Repository подтвердил увеличение версии, `OptimisticLockError` для повторной записи со старой версией и сохранность первого изменения при последующем чтении БД через `findBy`. Самостоятельное объяснение механизма ещё не подтверждено; уровень освоения не повышен.

## Evidence

2026-09-20: `pnpm exec vitest run --config vitest.config.ts src/repository/make-repository.test.ts` — 15 тестов прошли; `pnpm check-types` прошёл. Сценарий E4.4 использует SQLite: Anna/1 → Boris/2, затем отказ попытке Victor с ожидаемой версией 1; чтение вернуло Boris/2. До реализации тест последовательно обнаруживал отсутствие увеличения версии и неверный класс ошибки.

## Ограничения

Защита включается передачей `expectedVersion`; без опции метод сохраняет обычное поведение. Конфликт E4.4 на PostgreSQL и одновременные запросы отдельных соединений не проверялись. Мутационная проверка не выполнялась. Проверки неподходящих метаданных были временными сценариями наставника, не постоянными тестами.

## Опора для продолжения

Потребовалось разделить описание колонки и значение строки, ожидаемую и новую версии, типизированную ошибку и дефект. Приведение ограничено выражением колонки `Expr<number>` после проверки её метаданных. После объяснения последовательного сценария пользователь верно предсказал отсутствие конфликта при передаче новой прочитанной версии `2`. Это локальное понимание с помощью, не самостоятельное объяснение всего механизма.
