# 0041 — L3.22: nullability источника в типе выражения

## Контекст

Запись 0040 закрыла метаданные: `SourceMap` хранит `Source<T, N>`, флаги проверены утверждениями на
`Sources['c']['nullable']`. Оставался разрыв: флаг существовал, но на тип выражения не влиял наблюдаемо. Шаг L3.22
закрывает разрыв и вместе с ним упражнение E3.2 курса.

## Результат

Условный тип в `col` (`src/query/expression-builder.ts:41-45`):

```ts
) => Expr<
  S[A]['nullable'] extends true
    ? InferColumn<S[A]['table']['_columns'][C]> | null
    : InferColumn<S[A]['table']['_columns'][C]>
>;
```

Наблюдаемая проверка — не на возвращаемом типе `col` напрямую, а на типе строки результата после `select`
(`src/hw/e3-2.test.ts:31-54`). Из `ExecutableUpdate` тип извлекается через `infer`:

```ts
type RowOf<Q> = Q extends ExecutableQuery<infer R> ? R : never;
```

Три утверждения на одном запросе `selectFrom(users, 'u').innerJoin(posts, 'p', ...).leftJoin(comments, 'c', ...)`:

| поле projection       | источник       | объявление колонки | ожидаемый тип    |
| --------------------- | -------------- | ------------------ | ---------------- |
| `b.col('p','userId')` | inner, `false` | `integer()`        | `number`         |
| `b.col('u','bio')`    | from, `false`  | `nullable(text())` | `string \| null` |
| `b.col('c','postId')` | left, `true`   | `integer()`        | `number \| null` |

Этот набор проверяет обе причины появления `null` по отдельности: вторая строка — только объявление колонки, третья —
только форма запроса.

## Ответ на открытый вопрос: два источника `null`

Comprehension question шага L3.22 — что произойдёт с объявленной nullable колонкой из non-nullable источника. Открытая
неопределённость в `session.md` формулировала риск как `T | null | null` или потерю одного из двух `null`.

Ни того, ни другого не происходит. Объединения в TypeScript идемпотентны: `string | null | null` нормализуется в
`string | null`. Поэтому две причины `null` складываются без взаимного влияния, и порядок их применения не важен.

Наблюдение получено мутацией 2 ниже: когда обе ветви условного типа добавляли `| null`, утверждение на `userBio`
осталось верным, а сломалось только утверждение на `userId`.

## Мутационная проверка

Проверяемый код ломался двумя способами, каждый раз ровно на одном утверждении.

1. Обе ветви без `| null` (nullability источника игнорируется):

```text
src/hw/e3-2.test.ts(53,54): error TS2344: Type 'number | null' does not satisfy the constraint
  '"Expected: null, Actual: never" | "Expected: number, Actual: never"'.
```

Сломался только `postId` — единственное поле, чей `null` приходит от источника.

2. Обе ветви с `| null` (nullability источника приписана всем):

```text
src/hw/e3-2.test.ts(51,54): error TS2344: Type 'number' does not satisfy the constraint
  '"Expected: number, Actual: null"'.
```

Сломался только `userId`. `userBio` не сломался — это и есть наблюдение об идемпотентности.

Обе мутации ставились в возвращаемом типе `col` и снимались точечным редактированием той же строки.

## Проверка

- `pnpm check-types` — exit code 0 на исходном коде, exit code 1 на каждой из двух мутаций.
- `pnpm test src/query/builder.test.ts` — 7 passed; runtime-контракты terminals не задеты.
- Реальная строка с `null` от LEFT JOIN наблюдалась раньше, на шаге L3.20 (запись 0038). L3.22 привёл тип в
  соответствие с уже наблюдённым значением; повторного запуска на базе не выполнялось.

## Не покрыто

- Проверка идёт через тип строки результата, а не через `expectTypeOf` на самом вызове `b.col(...)`. Промежуточный
  `Expr<T>` наблюдается только косвенно, через `RowFromSelection`.
- Тестов на join во время исполнения в репозитории по-прежнему нет.
