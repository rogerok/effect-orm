# 0035 — Тесты трёх terminals и мутационная проверка

## Контекст

Три cardinality terminals были реализованы и проверены временными скриптами, которые удалялись после прогона. В репозитории защиты контрактов не было. Задача — закрепить контракты наблюдаемым тестом в стиле проекта.

## Результат

`src/query/builder.test.ts` содержит семь случаев: `execute` на нуле, одной и двух строках; `executeOne` на нуле и двух; `executeOneOrThrow` на нуле и двух. Прогон занимает около 330 мс.

Использованы существующие средства проекта: `it.effect` из `@effect/vitest`, `Effect.result` для приведения провала к `Result`, собственные матчеры `toEqualSuccess`, `toBeFailure` и извлекающий `expectFailure` из `src/config/result-matchers.ts`. Матчеры подключаются через `setupFiles` в `vitest.config.ts`, `expect` доступен из-за `globals: true`.

## Фейковый драйвер вместо реальной базы

Первая версия теста оборачивала фейк поверх слоя PGlite, чтобы взять у настоящего драйвера `dialect` и `executeStream`. Это поднимало базу ради двух полей в тесте, который до SQL не доходит; прогон занимал 2 с.

Обычный объект `DriverImpl` с `PgDialect` и `Stream.empty` устранил и слой, и зависимость от PGlite. Фейк принимает набор строк параметром и считает обращения к `executeRaw`.

## Число обращений к драйверу не связано с числом строк

Пользователь написал `expect(calls()).toEqual(2)` в тесте с двумя строками, связав два независимых числа. Прогон показал `expected 1 to deeply equal 2`.

Точная модель: `calls` считает обращения к драйверу, то есть количество запросов к базе; число строк — это то, сколько вернуло одно обращение. Один запрос возвращает ноль, одну или миллион строк при неизменном счётчике.

Счётчик покрывает дефект, который проверка значения не видит: мутация, заставляющая `execute` обращаться к драйверу дважды, оставляет результат верным. Утверждение `toEqualSuccess` при ней проходит, падает только `calls()`.

## Главное наблюдение: зелёный тест ещё не значит покрытый контракт

Первая полная версия из семи случаев была зелёной и выглядела законченной. Мутационная проверка показала иное:

| мутация                                   | поймана |
| ----------------------------------------- | ------- |
| `count: 1` при любом числе строк          | нет     |
| подмена `NotFoundError` на `TooManyError` | да      |
| `executeOne` всегда возвращает `None`     | да      |
| `execute` обращается к драйверу дважды    | да      |

Непойманная мутация — ровно тот дефект, который был в коде часом ранее. Причина: `toBeFailure(TooManyError)` проверяет только класс ошибки и не смотрит на поля.

После добавления `expect(expectFailure(result)).toMatchObject({ _tag: 'TooManyError', count: 2 })` повторный прогон поймал все пять мутаций, включая завышение `count` на единицу.

## Сравнение ошибки целиком не работает

`toEqualFailure(new TooManyError({ count: 2, sql: '...' }))` падает, хотя поля совпадают точно. Матчер сравнивает экземпляры целиком, а `stack` у двух объектов ошибки различается: проверено, `a.stack === b.stack` даёт `false`.

Следствие: поля ошибки проверяются поштучно через `toMatchObject`, а не сравнением с построенным экземпляром.

## Проверка

- `pnpm test` — 18 файлов, 67 тестов, все проходят.
- `pnpm check-types` — exit code 0.
- Пять мутаций `builder.ts` дают красный тест; после восстановления файла набор снова зелёный.
- Остаются неиспользуемые импорты `Result` и `TooManyError` в тестовом файле.

## Итог

Долг по наблюдаемым тестам закрыт. Контракты трёх terminals защищены от регрессии и проверены на способность краснеть.

Метод, который стоит переносить дальше: после написания теста намеренно ломать проверяемый код и убеждаться, что тест падает. Зелёный тест доказывает только то, что он умеет проверять.
