# 0032 — L3.10: `ExecutableQuery<R>` переносит границу FSM в runtime API

## Контекст

До этого шага `select` возвращал typed AST `Select<R>` — объект без методов. Он не запрещал ни `limit`, ни повторный
`select`. Compile-only FSM существовала только в упражнении `src/hw/e3-1.ts` поверх `declare const selectFrom`. Задача
L3.10 — перенести ту же машину состояний в реальный builder.

## Наблюдения

- Пользователь реализовал класс `ExecutableQuery<R>`, хранящий состояние запроса, и изменил возвращаемый тип `select` на
  `ExecutableQuery<RowFromSelection<Sel>>`.
- Пользователь до правки верно предсказал причину будущего запрета: `R` в нём не участвует, метода `limit` нет у класса
  `ExecutableUpdate`. Это ответ на comprehension-вопрос L3.10 о разнице между множеством методов класса и
  generic-параметром.
- Проверка типов подтверждает механизм: запрет даёт TS2339 `Property does not exist`, то есть разрешение метода по типу
  объекта. Значение `R` в проверке не участвует; в [typed-ast.ts:15](../../src/query/typed-ast.ts:15) `R` живёт в
  необязательном свойстве `[Brand]?`, которого нет в runtime.
- Разделение ролей: множество методов класса задаёт допустимые переходы, `R` задаёт тип результата. Без `R` метод
  `toIR()` возвращал бы `SelectIR` и тип строки был бы потерян.

## Граница `exactOptionalPropertyTypes` и способ сборки объекта

Первая версия `toIR()` перечисляла поля явно, включая `limit: this.state.limit`. Такая запись всегда создаёт ключ, в том
числе со значением `undefined`. При `exactOptionalPropertyTypes: true` запись `limit?: number` этот вариант запрещает,
поэтому появлялась ошибка TS2375.

Пользователь сначала снял ошибку, расширив общий `SelectIR` до `limit?: number | undefined`. Наблюдаемые последствия
этого варианта:

- `Object.keys` для запроса без модификаторов содержал `limit`, `offset` и `where`, а `'limit' in ir` возвращал `true`;
- `Hash.hash({ _tag: 'Select' })` не равен `Hash.hash({ _tag: 'Select', limit: undefined })`, при этом два структурно
  одинаковых объекта дают равный хеш. `makeCompileCache` индексирует `HashMap` по IR, поэтому IR из `toIR()` и IR без
  этих ключей были бы разными ключами кеша для одного запроса;
- SQL и params не менялись: compiler корректно обрабатывает `undefined`.

Итоговое решение — собирать объект через spread `this.state`, а `SelectIR` вернуть в исходный вид. Spread отсутствующего
необязательного поля ключ не создаёт. Локальный способ сборки не должен ослаблять общий тип для всех потребителей.

## Проверка

- `pnpm check-types` завершился с exit code 0.
- Positive type case: `const ir: Select<{ nick: string; userId: number }> = q.toIR()` принят без ошибки.
- Negative type cases: `limit`, `offset`, `where` и повторный `select` после `select()` дают TS2339. Строка с неверным
  типом результата отклонена. Принятый и отклонённый случаи различаются только типом строки, поэтому причина
  отклонения — тип строки.
- Runtime SQL для полного запроса:
  `SELECT "u"."id" AS "userId", "u"."name" AS "nick" FROM "users" AS "u" WHERE "u"."id" = $1 ORDER BY "u"."name" ASC LIMIT 20 OFFSET 5`,
  params `[10]`.
- Runtime SQL для запроса без модификаторов: `SELECT "u"."id" AS "userId" FROM "users" AS "u"`, params `[]`.
- После перехода на spread: `Object.keys` для запроса без модификаторов равен
  `["_tag","columns","from","joins","orderBy"]`, `'limit' in ir` возвращает `false`. Для полного запроса все восемь
  ключей присутствуют.

## Итог

L3.10 закрыт. Реализация выполнена пользователем с помощью; причинная связь запрета объяснена пользователем
самостоятельно до правки. Флаг `exactOptionalPropertyTypes` был включён по чужой рекомендации и его смысл пользователю
не был известен; объяснение дано на literal-примере, самостоятельное объяснение не подтверждено и требует retrieval
check.

Проверка выполнялась временными проверочными скриптами, удалёнными после прогона. В репозитории регрессионной защиты
этой границы нет: `src/hw/e3-2.ts` содержит только вызов без утверждений.

Следующий шаг — L3.11: `execute()` делегированием существующему typed `run`, без дублирования compiler и Driver.
