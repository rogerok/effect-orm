# E4.3: commit вставляет родителя раньше потомка независимо от порядка register

Пользователь с помощью реализовал порядок вставки по FK-зависимостям: чистую функцию `topologicalSort` (алгоритм
Кана, `Result` с `CyclicDependencyError`), `insertOrderEdges` над объектами `relations`, операцию очереди
`PendingOperation { table, effect }`, `register(table, effect)`, `makeUnitOfWorkLayer({ relations })` и сортировку
очереди в `commit` по позиции таблицы. Постоянный тест на SQLite с включёнными FK подтвердил: без связей commit
падает с `ForeignKeyViolationError`, со связями тот же сценарий вставляет пользователя раньше поста.

## Evidence

2026-09-24: `pnpm vitest run src/uow src/repository` — 45 тестов прошли; `pnpm check-types` прошёл.
Мутации: `inDegree.get(to)` → `get(from)` ловит только тест `sections → categories → posts` + `users → posts`
(граф `a → c`, `b → c` мутацию не ловит — оба родителя уже в FIFO-очереди); замена `sortedOperations` на
`pendingOperations` в commit роняет тест «со связями» (сообщение `expected +0 to be 1` — `expectSuccess` стоит после
выборок строк, рекомендовано переставить).

## Ограничения

- Сортируется вся очередь, включая UPDATE/DELETE; для DELETE нужен обратный порядок. `register` не знает вид
  операции. Вне E4.3.
- Связь таблицы на саму себя (`users.managerId → users`): пользователь сам предсказал ложный `CyclicDependencyError`
  и выбрал место исправления (`insertOrderEdges`, не `topologicalSort`) с верным обоснованием. Петли пропускаются;
  порядок строк внутри таблицы — порядок `register`. 46/46. Взаимные ссылки строк (INSERT с NULL, затем UPDATE)
  не реализованы.
- Тесты UoW-сортировки лежат в `topological-sort.test.ts`, а не в `unit-of-work.test.ts`.
- `relations.onDelete` стал необязательным `'cascade' | 'no action'` по инициативе пользователя.
- Третий тест `topologicalSort` написан агентом при отключённом наставнике.

## Опора для продолжения

Новые понятия с нуля: graph, DAG, in-degree, топологическая сортировка, алгоритм Кана. Ручная трассировка Кана
удалась после одного уточнения (входящее ребро). Направление in-degree (по `to`) в коде дважды перепутано — с
подсказкой исправлено. Разделение «операция несёт таблицу / схема передаётся один раз» не далось в абстрактной
форме; после конкретной трассировки и урока 0015 пользователь сформулировал его сам. Выбор Layer вместо параметра
commit обоснован с уточнением. Уровень — реализация с помощью.
