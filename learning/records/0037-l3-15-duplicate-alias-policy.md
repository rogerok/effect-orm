# 0037 — L3.15: политика повторного alias

## Контекст

`innerJoin` возвращает `SelectQueryBuilder<{ [K in A]: T } & S>`. Пересечение типов не проверяет, свободен ли ключ.
Шаг L3.15 требует, чтобы повторный alias либо отклонялся, либо имел явно задокументированную семантику, и чтобы молчащей
перезаписи не было.

## Наблюдения

`selectFrom(users, 'u').innerJoin(posts, 'u', ...)` проходит `pnpm check-types` без ошибок. Под ключом `u` становятся
доступны колонки обеих таблиц: `b.col('u', 'name')` из `users` и `b.col('u', 'title')` из `posts` компилируются в одном
запросе. Компилятор строит:

```sql
SELECT "u"."title" AS "both", "u"."name" AS "fromUsers"
FROM "users" AS "u"
INNER JOIN "posts" AS "u" ON "u"."id" = "u"."userId"
```

Поведение при исполнении различается по диалектам:

| запрос                                                | SQLite (better-sqlite3)                      | PostgreSQL (PGlite)                       |
| ----------------------------------------------------- | -------------------------------------------- | ----------------------------------------- |
| со ссылкой `"u"."id"`                                 | `ambiguous column name: u.id`                | `table name "u" specified more than once` |
| `SELECT 1 AS one ... ON 1 = 1`, без ссылок на колонки | выполняется, `{ rows: [], affectedRows: 0 }` | `table name "u" specified more than once` |

Отсюда вывод, который определил формулировку документации: безопасного применения повторного alias нет. PostgreSQL
отвергает сам `FROM`, SQLite — первую ссылку на колонку через занятый alias, а builder всегда строит ссылки через `col`.

Проверка выполнялась временными скриптами `src/hw/tmp-join-check2.ts` и `src/hw/tmp-alias-policy.ts`; оба удалены после
прогона.

## Решение

Пользователь выбрал третий вариант из трёх предложенных: не менять систему типов и не добавлять runtime-проверку, а
задокументировать поведение. Обоснование выбора не сформулировано; текст doc comment написан преподавателем по прямой
просьбе пользователя. Режим наставника при этом не отключался: правка не содержит поведения, следующий шаг остаётся
пользовательским.

Doc comment на `innerJoin` в `src/query/builder.ts` фиксирует три факта: alias обязан быть уникален; повторный alias не
отклоняется компилятором и объединяет колонки обеих таблиц под одним ключом; получившийся SQL отклоняется во время
исполнения, причём текст ошибки зависит от базы данных.

## Остаточный риск

Документация не устраняет расхождение: тип продолжает обещать набор колонок, которого в SQL не существует. Дефект
обнаруживается в самом дальнем от кода месте — в драйвере, на конкретной базе. Вариант с запретом на уровне типов
остаётся доступным и сводится к изменению типа параметра `alias`.

Критерий шага «политика обоснована конкретным дефектом» не выполнен: решение принято, объяснение не получено.
