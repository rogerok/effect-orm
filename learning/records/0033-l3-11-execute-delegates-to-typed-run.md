# 0033 — L3.11: `execute()` делегирует существующему typed `run`

## Контекст

`ExecutableQuery<R>` уже отделён от builder и умеет отдавать `Select<R>` через `toIR()`. Задача L3.11 — подключить исполнение, не создавая второй путь компиляции и не обращаясь к `Driver` напрямую из builder.

## Наблюдения

- Пользователь реализовал `execute()` как `run(this.toIR())` с явным типом `Effect.Effect<ReadonlyArray<R>, DriverError, Driver>`. `compile` из `builder.ts` не вызывается.
- Граница отложенного исполнения уточнена. Исходная формулировка пользователя — «`Driver` используется непосредственно в вызове `execute`» — не подтвердилась. Вызов `execute()` не обращается к `Driver`: счётчик `executeRaw` остаётся нулевым, а SQL появляется только при запуске Effect.
- Точная модель: `selectFrom` и модификаторы возвращают данные и требований не имеют; `execute()` возвращает описание вычисления, где `Driver` стоит в третьем параметре `Effect.Effect<A, E, R>` как объявленное требование; чтение сервиса происходит в момент исполнения.
- Один и тот же результат `execute()` можно запустить дважды: второй запуск дал второй вызов `executeRaw`. Значение является переиспользуемым описанием, а не сохранённым результатом.

## Диагностика `unnecessaryEffectGen`

Пользователь сначала написал `run(ir).pipe(Effect.map((v) => v))`, опираясь на подсказку language service. Проверка трёх вариантов под `tsc` показала:

| вариант                                               | диагностика                     |
| ----------------------------------------------------- | ------------------------------- |
| `Effect.gen(function* () { return yield* run(ir); })` | TS377017 `unnecessaryEffectGen` |
| `run(ir).pipe(Effect.map((v) => v))`                  | нет                             |
| `run(ir)`                                             | нет                             |

Правило `@effect/tsgo` предлагает удалить `Effect.gen`, а не заменить его другой обёрткой. Генератор с единственным `return yield* x` равен `x`, поэтому корректная замена — сам `x`. Функция `(v) => v` возвращает аргумент без изменений; правило её не проверяет, поэтому молчание language service не является доказательством осмысленности кода. Итоговая реализация — `return run(ir);`.

## Сравнение с эталоном курса

Раздел 3.6 курса реализует `execute()` иначе: внутри `Effect.gen` читает `Driver`, вызывает `compile`, вызывает `driver.executeRaw` и приводит `raw.rows`. Те же три шага повторяются в `executeOne` и `executeOneOrThrow`.

При этом курс сам определяет `typed-run.ts` с идентичным `run` в разделе 2 и в разделе 3.6 его не использует. Это расхождение внутри материала курса.

Эталонный `toIR()` перечисляет поля и завершает результат приведением `as Select<R>`. В этом проекте перечисление полей конфликтует с `exactOptionalPropertyTypes: true`, и приведение типа скрывало бы конфликт. Реализация через spread его устраняет и приведения не требует.

Расхождение с курсом запланировано roadmap L3.11: execution adapter не дублирует compiler и Driver pipeline.

## Проверка

- `pnpm check-types` — exit code 0. `pnpm exec oxlint src/query/builder.ts` — без предупреждений.
- Прогон с fake Driver: после вызова `execute()` вызовов `executeRaw` — `0`; после `Effect.runPromise` — `1`.
- SQL: `SELECT "u"."id" AS "userId", "u"."name" AS "nick" FROM "users" AS "u" WHERE "u"."id" = $1 ORDER BY "u"."name" ASC LIMIT 20`, params `[10]`.
- Результат: `[{"nick":"Ann","userId":1}]`; поля `userId` и `nick` читаются.
- Повторный запуск того же описания дал второй вызов `executeRaw`.

## Итог

L3.11 закрыт. Реализация выполнена пользователем; исходная неточность про момент обращения к `Driver` исправлена на наблюдении. Непроверенное приведение `raw.rows as unknown as ...` остаётся в одном месте, в `typed-run.ts`, и при делегировании не размножается.

Следующий шаг — L3.12: cardinality terminals с точными success values и `_tag` ошибок `NotFoundError` и `TooManyError`.
