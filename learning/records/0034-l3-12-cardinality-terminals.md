# 0034 — L3.12: cardinality terminals и цена непроверенного приведения типа

## Контекст

`ExecutableQuery<R>` умел только `execute()` для множества строк. Задача L3.12 — развести три контракта: много строк, первая строка, ровно одна строка. Ошибки `NotFoundError` и `TooManyError` уже существовали, но нигде не использовались.

## Результат

| строк в ответе | `execute`  | `executeOne` | `executeOneOrThrow`        |
| -------------- | ---------- | ------------ | -------------------------- |
| 0              | `[]`       | `None`       | `NotFoundError`            |
| 1              | `[r]`      | `Some(r)`    | `r`                        |
| 2              | `[r1, r2]` | `Some(r1)`   | `TooManyError`, `count: 2` |

Пользователь верно определил, какой контракт считает две строки допустимыми: только «ровно одна» делает утверждение о данных, которое можно нарушить и потому нужно проверять.

## Откуда взялся `sql` для ошибок

Делегирование из L3.11 создало проблему: `sql` знал только `run`, который вычислял его и терял. Рассматривались три источника — вычислить заново в terminal, отдавать из границы исполнения, убрать `sql` из ошибок. Пользователь выбрал второй.

В `typed-run.ts` добавлен `runWithSql`, возвращающий результат и `sql`; `run` переопределён как `runWithSql(stmt).pipe(Effect.map((r) => r.result))`. Логика `hasReturning` осталась в одном месте, публичный тип `run` не изменился, пять существующих мест вызова не тронуты.

## Главное наблюдение: `as unknown as` скрывает ошибку формы

При переносе тела в `runWithSql` форма результата ломалась трижды подряд, и каждый раз `pnpm check-types` проходил без единой ошибки:

1. `result: { rows: raw.rows }` — лишняя вложенность. `execute()` вернул `{"rows":[...]}`, `Array.isArray` дал `false`, `executeOne()` вернул `Some` без значения.
2. Вторая ветка вернула поле `result`, тогда как интерфейс объявлял `rows`. `run(DELETE)` вернул `undefined`.
3. Вторая ветка подняла `affectedRows` на верхний уровень рядом с `sql`. `run(DELETE)` снова вернул `undefined`.

Причина одна: приведение `as unknown as RunWithSqlResult<S>` стояло на всём возвращаемом объекте, поэтому проверялось только наличие `sql`, а форма результата — нет.

Устранено переносом приведения на одно значение:

```ts
const result = (
  hasReturning ? raw.rows : { affectedRows: raw.affectedRows }
) as StatementResult<S>;

return { result, sql };
```

Внешний объект после этого проверяется обычным образом, ветка `return` одна, и ошибка того же класса стала бы ошибкой компиляции.

## Сужение типа элемента массива

Проверено изолированно: проверка `rows.length === 1` не сужает тип `rows[0]` — при `noUncheckedIndexedAccess: true` он остаётся `T | undefined` (TS2322). Сужает только сравнение самого значения с `undefined`.

Первая версия обходила это через `Array.head`, из-за чего тип успеха «ровно одной» строки оказался `Option<R>` и совпал с контрактом `executeOne`. Итоговая версия проверяет `result[0] === undefined`: та же проверка закрывает случай нуля строк и сужает значение до `R`.

## Канал ошибки против канала успеха

Проверено на исполнении: `return new NotFoundError({ sql })` помещает ошибку в канал успеха, тип становится `Effect<NotFoundError | ..., ...>`. `return yield* new NotFoundError({ sql })` помещает её в канал ошибки.

Классы `Data.TaggedError` в Effect 4.0.0-rc.108 передаются в `yield*` напрямую; обёртка `Effect.fail` вызывает диагностику `unnecessaryFailYieldableError`, а голый `yield*` без `return` — `missingReturnYieldStar`.

## Проверка

- `pnpm check-types` — exit code 0. `oxlint` по `builder.ts` и `typed-run.ts` — без предупреждений.
- `pnpm test` — 17 файлов, 60 тестов, все проходят. Существующие вызывающие стороны `run` не сломаны.
- Прогон против нуля, одной и двух строк подтвердил таблицу контрактов; `sql` заполнен в обеих ошибках, `count` равен фактическому числу строк, на каждый terminal приходится один вызов `executeRaw`.
- `run(DELETE)` без `returning` возвращает `{"affectedRows":3}`; `run(SELECT)` возвращает массив.

## Итог

L3.12 закрыт. Реализация выполнена пользователем; форма результата в `runWithSql` и способ сужения типа потребовали показанного кода после трёх неудачных попыток.

Наблюдаемых тестов на три контракта в репозитории по-прежнему нет: всё проверялось временными скриптами. Это ближайший долг перед переходом к L3.13.
