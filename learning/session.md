### Реализовано и проверено в этой сессии

- `src/query/builder.ts`: все три терминала `ExecutableQuery` передают `state.sources`.
  `src/query/typed-run.ts`: `RunOptions` принимает `sources`, `run` передаёт объект опций целиком
  в `runWithSql`. Метаданные остаются вне IR.
- `getCodec` находит фабрику через псевдоним таблицы и имя колонки, получает кодек текущего `Driver`.
  `encodeLiteral` кодирует второй аргумент по колонке из первого. Если пара не `Column`/`Literal`,
  значение равно `null` или кодека нет, возвращает исходное выражение.
  Исключение `encode` оборачивается в `CodecError` с колонкой, доменным значением и исходной причиной.
- `encodePredicate` рекурсивно обрабатывает `And`, `Or`, `Not`; общая ветка для
  `Eq`, `Neq`, `Gt`, `Gte`, `Lt`, `Lte` сохраняет оператор и стороны через копирование предиката.
  В `In` значения кодируются по `left`; в `Between` обе границы кодируются по `expr`,
  если `expr` — колонка. Остальные виды предикатов возвращаются неизменными.
- Результат подготовки заменяет `where` в копии SELECT, передаваемой в `compile`.
  Объединение старого и подготовленного условий через `And` было ошибкой:
  старое условие сохраняло boolean-параметр, поэтому SQLite продолжал отказывать. Пользователь исправил.
- `src/query/make-repository.test.ts`, `check bool with where`: две строки записываются через `save`,
  оба фильтра возвращают точные строки `{ id: 1, active: true }` и `{ id: 2, active: false }`.
  Одного поиска по первой строке было недостаточно: отсутствие фильтра могло остаться незамеченным.
- В том же файле `where codec error`: таблица и строка подготовлены сырым SQL, SELECT фильтрует
  `label = 'needle'`, тестовый `encode` выбрасывает заранее созданный `encodeErr`.
  `Effect.result` позволяет проверить `CodecError`, `cause` через `toBe(encodeErr)`,
  а `column: 'label'` и `value: 'needle'` — через `toMatchObject`.
- Временные сценарии Node/tsx на настоящем SQLite подтвердили: `Or` с вложенным `And`,
  `Not`, `Neq` с литералом с обеих сторон, восемь случаев четырёх сравнений порядка,
  `In` с `true`/`false`/`null`, четыре диапазона `Between`.
  Проверены точные строки и неизменность исходного IR. Проверочные файлы не создавались.
  Эти сценарии не являются постоянными тестами.
- Ошибка `Between` воспроизведена: кодек ошибочно искался у соседней границы, параметры оставались
  `[false, true]`, SQLite выдавал `DbError`. После выбора кодека по `expr` прежний сценарий прошёл.

### История E3.5

Реализация закреплена семью постоянными тестами; самостоятельное воспроизведение пользователем ещё не подтверждено.

Базовая линия перепроверена запуском Node/tsx на SQLite `:memory:` без создания файлов:
проекция `{ id: b.col('f','id'), enabled: b.col('f','isActive') }` над колонкой `bool()` вернула
`[{ id: 1, enabled: 1 }, { id: 2, enabled: 0 }]`, `typeof` обоих значений `enabled` — `number`.
Тип `R` при этом обещает `boolean`. Это исходное поведение E3.5, а не его реализация.

Исходная причина: `col` сохраняет только `{ _tag: 'Column', table, name }`,
`SourceMap` существует только при проверке типов, а `runWithSql` возвращает `raw.rows`
без декодирования.

Пользователь добавил `BuilderState.sources: Readonly<Record<string, AnyTableDef>>` и
`sources: { [alias]: table }` в `selectFrom` после объяснения и указания формы словаря.
`pnpm check-types` — код `0`. Временный сценарий Node/tsx подтвердил сохранение исходного
объекта таблицы после `limit`/`select` и поиск кодека по выражению переименованной колонки.
Прямой вызов декодера SQLite преобразовал `1`/`0` в `true`/`false`.
Автоматическое декодирование через `execute` ещё не реализовано и этим сценарием
не проверялось. Файлы для сценария не создавались.
Самостоятельное проектирование связи проекции с метаданными пока не подтверждено.

Пользователь добавил новый словарь `sources` в `innerJoin` и `leftJoin`, сохранив прежние
источники и зарегистрировав `[alias]: table`. Также `toIR` исключает `sources`.
`pnpm check-types` — код `0`. Временный сценарий Node/tsx проверил оба JOIN, сохранение
ссылок на исходные объекты таблиц, независимость исходного и производных запросов,
накопление трёх источников при последовательных JOIN и поиск кодека колонки присоединённой
таблицы после `select`. `sources` отсутствует в IR. Для проверки метаданных сценарий
читал состояние объектов из JavaScript; SQL не выполнялся. Файлы не создавались.

Пользователь верно предсказал поведение проверки лишних свойств (excess property check).
Подтверждено compiler API TypeScript 6.0.3 на виртуальном исходнике без создания файлов:

- `selectAll` и все три метода исполнения возвращают декодированные строки.
- INNER/LEFT JOIN сохраняют привязку колонок к псевдонимам; `null` не превращается в `false`.
- Диалект для кодека определяется Driver при исполнении, а не при построении запроса.
- Ошибка декодера передаётся как `CodecError` с полем результата, исходным значением и причиной.
- Повторное исполнение не меняет исходные строки Driver.
